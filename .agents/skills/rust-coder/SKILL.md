# Rust Coder

**Execution.** Establish the observable result and choose the data representation that makes the operation clear. When requirements meet on the same input or transition, decide their precedence before choosing mechanics. Honor supplied requirements and preserve settled choices outside the requested change; resolve only what the task leaves open.

Read the affected code and callers against the accepted behavior; extend the current owner and repair in-scope mismatches instead of copying them. In this service, the composition root owns lifecycle, config owns its typed snapshot, health owns readiness, provider adapters own integrations, and features own business decisions. Routes, keys, and background work join those existing paths. A standalone module follows its own callers and constraints; it does not acquire service crates, runtime, or workflow machinery from this skill.

**Reuse.** Identify what the representation already guarantees, such as ordering, uniqueness, contiguous storage, or exclusive ownership. Use those facts to choose an operation that directly expresses the change. Check existing code, standard-library APIs, and declared dependencies for matching semantics. Before implementing a general parser, serializer, or scheduler, compare the custom logic and failure handling with a maintained library; a dependency-free implementation is not automatically simpler. Use rust-dependencies when available for that choice, respecting a fixed std-only task. A new abstraction, alias, entry point, option, or generic parameter needs a current constraint, caller, or dependency direction. Keep each rule in one place, but extract only when the cases share that rule: similar text is not shared knowledge, and an abstraction that keeps growing flags should be undone. Keep new items private until a caller needs them.

**Clarity.** A reader should understand the code quickly: make the main transformation, mutation boundary, and failure paths visible. A function does one thing, and its acceptable length falls as complexity and nesting rise; a long flat match can be fine, a dense branching body is not. Extract a part when a name can state what it achieves so the reader can skip how; keep together pieces that must be read together. Flatten with early returns, and move a condition to the caller when the caller has the context, expressing the precondition in the callee's types. Prefer a plain function to an object created only to run one action; a function with a clear receiver is a method, and it returns values rather than filling out-parameters. Prefer an existing operation when it removes manual phase flags, restoration paths, or duplicated traversal without obscuring the algorithm. After a correct draft, reconsider that central transformation once; a clearly simpler equivalent deserves the change, not a speculative rewrite. Updating a bounded region can preserve an existing owner or buffer; producing a new independent result can justify building fresh storage. Neither in-place mutation nor fewer lines is a universal goal. Do not write code slower than it needs to be: avoid a needless Vec, String, or collect, and reserve capacity when the size is known. Keep pure business decisions free of I/O within their existing owner; add no layer solely for that separation.

Inspect the far side of each changed boundary: callers, ownership transfer, drop order, and completion obligations. Match surrounding names and the project's comment and style rules. Where a doc comment exists, its first line is a one-sentence summary, errors and panics go under `# Errors` and `# Panics`, examples use `?` rather than unwrap, and prose links related items. A wrong comment is worse than none, so change it with the code. Work in behavior-sized changes with independent expectations. Reuse adequate tests; choose missing cases from accepted behavior, not current output. Bound waits and observe tasks. For a bug with an available reproducer, establish that it fails for the reported reason before fixing it; a compile error does not prove regression detection.

Use the existing validation policy and available tools. In this workspace, AGENTS.md's Validation budget selects the checks and owns lockfile policy. Without a project policy, format, build, run relevant tests, and use Clippy on the affected targets. Resolve an initial or deliberately changed dependency set before locked validation. Exercise the runtime boundary when compilation cannot establish the requested behavior, such as startup schema execution or process shutdown. An empty test run proves no behavior, and a passing command before the final edit does not cover that edit. Fix a finding or justify a narrow exception; do not create a workspace, runner, or environment solely because this method mentions one.

For review, explain the concrete risk and smallest justified change without editing. For implementation, finish when the requested outcome and required checks are satisfied. Continue repairing a known in-scope defect when tools and inputs allow it; disclosing that defect is not completion. Respect an explicit request to defer tests or stop at a named phase, and state unavailable verification or a concrete blocker without claiming a pass. Report impact and distinguish introduced failures from unrelated baseline failures. Do not add unrelated cleanup or proof gates.
