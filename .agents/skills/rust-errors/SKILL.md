# Rust Errors

**Failure semantics.** Follow failure from the operation that knows what happened to the consumer that must act on it. Distinguish rejected work, partial effects, uncertain outcomes, and completed work whose reporting or cleanup failed. Each boundary decides whether to stop, degrade, retry, or continue. Honor supplied requirements and preserve settled choices outside the requested change; resolve only what the task leaves open.

Design errors for their consumers. Preserve typed distinctions where a caller chooses recovery; an application boundary that only reports and exits may use an existing contextual error type. Do not create variants nobody consumes merely because code is in a crate. Public library error types implement std::error::Error, Display, and Debug, including when their variants already existed; Result itself imposes no such bound, so interoperability is an API decision the compiler does not supply automatically. Keep required variants and upstream causes. Reuse the project's established implementation: this service uses thiserror; a small standalone error can implement the standard traits manually without a new dependency.

At the operation that knows the failed action, retain the safe resource identifier or input position needed to locate it. A rejected record should identify the record and failed rule when disclosure is permitted. Preserve a source when there is one, and check the diagnostic actually rendered: storing a source does not ensure the reporting boundary displays it. Keep error text concise and composable, with lowercase text and no trailing punctuation where the project's convention requires it. Redact sensitive values throughout the chain, not only in the outer message. Preserve required precedence among failures and any promise of all-or-nothing output.

Use From for canonical conversions that need no call-site context. Use map_err to attach operation-specific context or convert a foreign error, and match when choosing recovery behavior. Classify structured failures by their kind rather than display-string matching. A retry needs knowledge of the operation's effect and identity; a timeout or broken connection does not by itself prove that nothing happened. An intentionally ignored cleanup failure needs an accepted best-effort policy; a printed error followed by a success result otherwise misleads callers and automation. Help or another successful early termination is a normal outcome, not an empty error sentinel.

When resource completion can fail, lose data, or wait, expose an explicit operation whose owner observes its outcome within the accepted lifecycle. Drop handles infallible release or best-effort cleanup without panicking or blocking; destruction does not establish durable flush or asynchronous completion. Keep the original operation outcome distinguishable from a later cleanup failure, and do not promise rollback where effects may already have escaped.

Follow the project's panic policy. Expected invalid input and external failures normally return Result; panic is not an error-propagation mechanism. In this workspace, the production panic, unwrap, and expect restrictions in [AGENTS.md](../../../AGENTS.md#rust-change-surface) apply. A task-boundary catch_unwind can provide defense in depth only when unwinding occurs; it neither repairs an interrupted invariant nor covers aborts. Observe spawned-task failures through their owner. Do not introduce a panic or silently recover poisoned state merely to simplify an error path.

In this service, [HTTP architecture](../../../docs/architecture/http.md) owns client-visible Problem responses: service-failure owns the catalog and infra-http its transport projection. [Runtime lifecycle](../../../docs/architecture/runtime-lifecycle.md) owns startup, degradation, shutdown outcomes, and exit policy. Preserve those mappings and sanitization at their current boundaries rather than inventing a parallel catalog or process-exit path. A standalone program does not acquire service telemetry or exit codes from this method.

For review, explain the failure policy, observable consequence, and smallest justified change without editing. For implementation, reuse adequate coverage and prove the changed mapping at the boundary that consumes it, such as a caller's typed recovery, HTTP response, or process exit and stderr. Report what was exercised. Neither a new error framework nor tests for every failure named in this skill are completion requirements.
