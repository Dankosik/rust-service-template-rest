# Rust Testing

**Behavior first.** Identify the observable promise a change could break, then choose the smallest layer that can watch it fail. Assert what a caller, client, or operator sees: status, body, problem code and headers, committed rows, a published message, a log record or metric, an exit code. Use expected literals or independently stated properties derived from accepted behavior, never the implementation's current output or a helper that mirrors it. Honor supplied requirements and preserve settled choices outside the requested change; resolve only what the task leaves open.

Choose the smallest layer that observes the promise. This service provides unit tests beside the owner, the mounted router, a bounded loopback server, the built binary for lifecycle and exit codes, and the integration-tests crate against Compose services. A standalone program uses its own available harness, not a new service workspace. Drive the interface its callers use. A test coupled to incidental layout or choreography breaks under a behavior-preserving refactor. Call counts, Debug output, or statement text need an actual observable contract, such as no duplicate effects or secret redaction. A status-only assertion proves neither order nor fallback, and a leaf handler called directly omits the chain.

Use the real dependency when its behavior is part of the claim and the project's selected harness can observe it: a real type over an invented internal interface, or a loopback protocol peer over a stubbed client. Follow this service's [database validation owner](../../../docs/validation/postgres.md) when actual database behavior is the promise; do not create a second container harness. A double can control an otherwise unavailable provider, nondeterministic input, or fault, but it must not implement the behavior under assertion. A passing interaction with a double is not proof of the real provider's semantics.

Control time and coordination separately. Code tested with paused Tokio time must use the compatible clock. Advance to the relevant boundary when the test needs that control, accounting for automatic advancement when the runtime is idle. Synchronize on an observable state change, notification, or joined task rather than assuming a sleep establishes order, and bound waits. For process proof, observe readiness before sending the shutdown signal and wait for the child to terminate. Use the current harness's signal and cleanup facilities rather than prescribing a new process wrapper.

Organize tests by behavior rather than method. Keep expected results independent of the implementation instead of restating its constants or mirroring its branches. Setup, coordination, tables, and independent properties can contain useful logic; distinguish them from an oracle that recomputes the answer the same way as production. Keep fixtures small, name each test for the rule it proves, and preserve contract distinctions such as a length exactly at a limit. A round trip alone can miss matching encoder/decoder errors; use an independent wire expectation when compatibility is the promise.

For a defect, write the test first and watch it fail for the reported reason. For a parser, encoder, or validator, use a bounded independent property when it covers material combinations the existing cases miss. To judge a suite here, make mutants PKG=crate FILE=path lists mutations no test catches; a survivor may expose a test gap, equivalent behavior, an unreachable mutation, or an unexercised configuration. Establish the changed observable before adding a test; do not maximize the mutation score.

For review, assess whether the tests distinguish the relevant defect without editing. For implementation, use the project's selected checks, leave no running task, and report exercised behavior. Check that the intended cases actually ran: a successful command with zero tests, an excluded target, or an ignored case does not establish its behavior. Compilation cannot execute a runtime schema or prove shutdown; use the available process or dependency boundary when that is the promise being changed. Respect an explicit deferral of execution and report the resulting proof gap. A mutation run, Miri, fuzzing, or a feature matrix is a discovery tool, not a completion gate.
