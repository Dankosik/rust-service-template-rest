# Rust Idiomatic

**Contracts.** Make ownership and caller expectations visible in ordinary Rust: admissible states, permitted transitions, who may mutate a value, and what absence or failure means. A type proves only the invariant its construction and operations enforce; it does not establish freshness, durable completion, or the lifetime of an external resource. Honor supplied requirements and preserve settled choices outside the requested change; resolve only what the task leaves open.

Borrow the data a reader needs, usually through slices, string slices, or paths. Take a value by ownership when the operation retains or consumes it. Inspect scope and data flow before adding a clone or shared owner. A deliberate copy or Rc/Arc can be appropriate when it supplies required sharing or makes ownership substantially easier to understand within the cost constraints; cloning is not wrong by spelling. Prefer owned fields unless a borrowed view earns the lifetime carried by its containers. Keep concrete parameters in application code when broader conversion or iterator inputs add no benefit to actual callers.

Use exclusive mutation where possible. Interior mutability and shared ownership need an identified invariant and access protocol; an Arc clone shares an allocation, not synchronized mutation. Check the Send, Sync, and lifetime requirements of actual task or thread crossings without imposing them on deliberately thread-local types. Borrow retained state in place when a transition only inspects or updates it. Move a payload out with take or replace when ownership really transfers, keeping the replacement state valid on every subsequent exit. The [ownership example](references/ownership.md) distinguishes a transfer from a snapshot and a restoration obligation. RAII releases resources on normal scope exit and unwinding, but aborts and leaked values can bypass destruction. Fallible, durable, or asynchronous completion needs an explicit operation whose outcome is observed; Drop alone cannot establish it.

Model mutually exclusive states with an enum carrying the data each state permits. Keep independently varying facts independent, as the [representation example](references/representation.md) shows. Use Option when absence is a distinct state; an empty string or collection is sufficient when empty and absent mean the same thing. Decode external sentinel conventions at their boundary. Prefer named fields outside very local code, standard types for quantities such as durations and paths, and newtypes when distinct units or identifiers are plausibly confused. A type alias does not prevent interchange. Replace an unclear boolean argument with a meaningful alternative, while leaving a clear independent boolean alone.

Parse and validate at the owning boundary, then carry the checked property inward where useful. Trace every construction and mutation path, including deserialization, conversion, defaults, and exposed fields: a constructor does not close bypasses elsewhere. Keep invariant-bearing fields private; passive data need not acquire getters. A builder is useful when optional inputs, construction variants, or incremental configuration make constructors hard to use. Straightforward construction and fallible validation alone do not require one. Typestate can prevent wrong-order calls but must justify its generic and API cost against an ordinary enum.

Implement standard traits when their semantics fit. Prefer From for lossless conversions and TryFrom when conversion failure matters; use as when its precise casting semantics are intended. Implement From rather than Into, whose blanket implementation supplies the other direction. An infallible zero-argument new normally agrees with Default. Keep ordinary functionality in inherent methods; a forwarding method may aid discovery alongside a trait. Put bounds where operations need them, retaining bounds required by the representation. Decide whether actual consumers require dyn compatibility before designing the trait.

Derive an implementation when it has the required meaning. Public types provide useful Debug, and intentional user-facing text uses Display; write formatting explicitly when its representation or redaction requires it. Library error types follow the error method and preserve useful causes. Published libraries anticipate common trait needs that downstream crates cannot supply; application code adds traits for current use. Keep equality, ordering, and hashing coherent: Ord returns Equal exactly when equality holds, partial ordering agrees, and equal values hash equally. Do not add ordering merely to complete a trait list. Use Deref for smart-pointer-like access, not inheritance, and operators for their mathematical or logical meaning. Mark results whose accidental discard defeats correct use as must_use when their type does not already express that obligation.

Use iterators for readable transformations and loops when state, effects, or early exits are clearer. Choose collections by required operations, ordering, and retained storage; a sorted map provides key order, not insertion order. Make arithmetic overflow and byte-versus-text semantics explicit where they affect the contract. The [collections and flow example](references/collections-and-flow.md) covers replacement and failure timing. Names communicate meaning and ownership: as_ exposes a cheap view, to_ converts without consuming a non-Copy receiver and may allocate, and into_ consumes; prefixes are not measured cost. Follow established iterator, getter, and constructor conventions, using domain verbs when they describe the resource operation better.

For review, explain the violated contract or concrete comprehension cost without editing. For implementation, preserve the current API constraints, format the change, and use the project's focused checks for the affected behavior or type contract. Follow its safety policy; this workspace forbids unsafe code. Do not modernize unrelated code or add types, traits, lifetimes, or validation merely to resemble an example.
