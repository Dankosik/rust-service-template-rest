# Rust Dependencies

**Resolution.** Compare the behavior and maintenance the application would own with the dependency's compatibility, operating, and supply-chain costs. Prefer a maintained crate for a non-trivial general mechanism when it meets the requirement; a smaller dependency count alone does not establish simplicity. Honor supplied requirements and preserve settled choices outside the requested change; resolve only what the task leaves open.

Check the existing owner, standard library, and installed dependencies first. If they leave a gap, evaluate a suitable maintained crate before writing the mechanism. Use official documentation for the version actually selected, including its defaults, features, and failure semantics. CLI grammar, serialization, date parsing, hashing, and parallel execution are examples of mechanisms with reusable implementations, not a mandatory crate list. A tiny fixed grammar, an explicit std-only constraint, or a concrete compatibility or operating limit can justify custom code. State that reason rather than treating the absence of a dependency as a benefit by itself.

Scale research to the open choice. A routine library addition needs evidence that it fits the behavior, toolchain, license, and relevant trust constraints, with a brief rationale in the existing change record. Reuse current evidence. Compare alternatives in depth when they materially differ in guarantees, maintenance, compatibility, or operating cost, or when an upgrade or new trust boundary makes those questions consequential. In this service, a new capability records that decision in its accepted artifact under specs. A standalone crate uses its own change record; this skill does not create a specs tree, scratch project, or full architecture study as the price of using a library. Apply the same scrutiny to custom general mechanisms.

Follow the project's manifest layout. In this workspace, declare shared versions once, disable default features, and enable the required features per crate. Inspect resolved features and duplicate versions when the change can affect compatibility, footprint, or provider behavior; successful resolution alone does not establish runtime delivery. For telemetry changes here, the `Cargo.toml` comment on the OpenTelemetry family records how its versions move together. A standalone package does not acquire workspace tables, telemetry rules, or service crates from this skill.

Separate dependency changes from validation. Initial resolution or an accepted dependency change deliberately generates or updates Cargo.lock through Cargo; inspect and include that diff with the declarations. Subsequent build and test commands use --locked so validation cannot silently change the selected graph. Do not edit lockfiles by hand or bypass integrity checks to repair a download. A cache lock or missing offline package is an environment limitation, not evidence that the library is unsuitable; use an available authorized route without clearing shared caches.

Keep the existing toolchain and edition unless changing them is part of the task. In this service, the exact pin and workspace minimum version move together in a reviewed change; afterwards `make modernize-scan SINCE=<previous toolchain>` lists code that the newer std forms and lints now cover, as candidates to judge rather than a gate. A declared minimum version is not proof of compatibility; select the relevant existing check rather than upgrading to obtain an incidental API. Review advisories, licensing, and build scripts or procedural macros in proportion to the changed trust surface.

For analysis, explain the proposed or failing resolution without editing. For implementation, finish with justified declarations, reviewed resolution, and the project's selected checks; absent a project policy, build and test the affected package against its lockfile. Report unavailable checks and CI-owned proof honestly. All-features success does not prove the default path, and compilation does not prove runtime semantics. Neither a benchmark, a dependency-wide audit, nor a new research artifact is a universal completion gate.
