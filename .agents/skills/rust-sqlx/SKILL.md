# Rust SQLx

**Durable outcome.** Follow database access from admitted connection and operation identity through execution, commit, and the caller's next safe action. Distinguish rejected work, a confirmed rollback, an uncertain commit, and cleanup of local resources. Honor supplied requirements and preserve settled choices outside the requested change; resolve only what the task leaves open.

When working in this service, load the [persistence architecture](../../../docs/architecture/persistence.md) and [database validation owner](../../../docs/validation/postgres.md). They select the retained profile's connection, pool, repository, migration, lifecycle, and command boundaries. If a required profile is absent, report the unavailable capability to the current task owner rather than prescribing missing providers or silently adding persistence. A standalone application follows its own accepted database boundaries.

Keep connection sources, session configuration, credentials, and diagnostics under their admitted owner. Reuse the shared pool and named operation acquisition where the project requires them. Transaction control belongs to the accepted transaction owner, but not every query necessarily requires an explicit transaction: native query-pool and autocommit operations can have their own valid scope. The migrator may own a dedicated session with a separate lifetime. Do not replace these distinctions with a universal closure wrapper or an independently created connection.

Choose a transaction for the invariant it must preserve, including the isolation and locking behavior needed under concurrent operations. Keep external effects and retry identity visible across the transaction boundary. Read the commit classification rather than treating any returned error as non-commit. This service distinguishes CommitFailed, where its evidence establishes failure, from CommitUnknown, where reconciliation under the same operation identity is required. Timeout, cancellation, local connection disposal, or a lost response alone cannot establish that the server did not execute or commit. Serialization failures and deadlocks reach the caller's accepted retry policy; a generic replay loop cannot decide whether earlier effects are safe to repeat.

Preserve the schema's migration authority and compatibility requirements. Here applied migrations are immutable and changes are forward-only. The normal transactional migration path has a guarded nontransactional exception for statements the database refuses inside a transaction; follow the [migration policy](../../../migrations/README.md) for replay safety, partial artifacts, and recovery. A query change does not authorize rewriting history. Review dynamic SQL through the actual input, binding, and query contract, and keep generated metadata consistent with the accepted schema.

Select proof by the claim. Configuration admission, failure classification, and rendered budget rules may have adequate unit evidence. Observed transaction, locking, commit, migration, or readiness behavior needs the project's real-database path; a compile or a test that never contacts the database cannot establish it. Reuse the required harness rather than creating a second environment. Keep query compilation, schema drift, and runtime semantics as separate evidence.

For review, trace affected access and writes to their admission, transaction or autocommit owner, commit-outcome handling, and migration policy without editing. For implementation, extend that owner, preserve failure and cancellation semantics, and run the selected checks for the behavior being claimed. Report the server and boundary actually exercised or the unavailable proof. This skill does not require a database run for an unrelated pure transformation or grant authority to operate production data.
