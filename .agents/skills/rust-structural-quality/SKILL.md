# Rust Structural Quality

**Deletion test.** Judge a structure by the responsibility it owns and the facts a reader or caller must coordinate. Keep it when its interface makes that responsibility easier to understand, preserve, or change; collapse it when it only relocates the same reasoning.

Use the current project's ownership and dependency boundaries. The [repository architecture](../../../docs/repo-architecture.md) names the composition, leaf, provider, and feature owners. A new crate needs a present reason such as dependency direction, a compile-time boundary, or an independent lifecycle; a tidy name is insufficient. Split modules by coherent responsibility or authority, not an arbitrary size threshold. Create a directory only when its first real artifact needs it.

A trait serves actual variation, generic programming, an erased consumer, or an extension; it is not needed merely to organize code. Choose a concrete type for fixed behavior, an enum for closed alternatives, generics for required static variation, and `dyn` for a consumer needing erasure or heterogeneity, accounting for API, code-size, and compilation constraints. Prefer an existing standard trait when its contract fits. A custom trait that only enables mocking internal choreography is a collapse candidate, and a macro must earn the work that functions, generics, or traits would otherwise own.

A private function used once is justified when its name, inputs, result, and failure behavior express a complete decision that the caller can understand without reading its mechanics. Validation or transformation can be such a responsibility; keep trivial forwarding and fragments tied to a caller's local state inline. A meaningful receiver makes an operation a method; an object created only to invoke one action usually exposes a function instead, and a local wrapper defined only to run one `Drop` closure or adapt a trait already satisfied by `std` or a declared crate collapses to that primitive unless it enforces an invariant across functions, while a private context struct may still clarify ownership. The [responsibility examples](references/responsibility.md) distinguish useful factoring and dependency boundaries from extra indirection. Names such as manager, service, or helpers invite an ownership check; they do not establish a defect by themselves.

Trace one realistic change. Pieces that must change together form a hidden link when their relationship is only a copied rule, an undocumented call order, or state written and interpreted in separate places. Keep that rule with one owner, or make the compiler or an appropriate test expose the relationship. When crates sharing such a rule have no common owner, that owner is `crates/shared-rules`, under the membership test in its crate documentation. An exhaustive match already makes a new variant visible, so repeating its cases is not equivalent to a silent policy copy. Similar text with independent reasons to change can remain separate, and a shared abstraction that accumulates flags prompts a check for diverging responsibilities rather than automatic extraction or deletion.

Cut unnecessary links before adding layers: use privacy, a narrower parameter or result, or a moved decision when a caller depends on internals or an interface changes with unrelated workflows. Search for the existing owner before adding another loop, error classifier, configuration source, or adapter. Avoid speculative capabilities, while recognizing reduced present comprehension and change cost as a valid benefit.

Keep unnecessary observable surface small. A public API creates compatibility obligations; do not add duplicate user-facing paths without a consumer reason. Internal re-exports and a deliberate facade can organize a crate without creating competing public APIs. Retain parallel paths, compatibility shims, or fallbacks only for an accepted current need with an owner, observable selection, and a removal condition. Before deleting a check, adapter, staging area, or recovery branch, name the behavior it preserves and where that behavior will remain. Removing a container that provides rollback, or a wrapper that preserves a required error response, is not simplification of the complete operation.

Line count, naming taste, and syntax preference alone are not blocking review findings, and no new framework, test seam, or proof gate is required merely to justify a structure.
