# Rust Structural Quality

**Deletion test.** Judge each added structure by asking which current responsibility or constraint would become harder to satisfy if it were removed. Honor supplied requirements and preserve settled choices outside the requested change; resolve only what the task leaves open.

Ownership boundaries are crates, and the crate graph is the dependency rule: the service crate composes; the config, health, and infra crates are leaves that never import one another's policy; feature crates depend on no transport or provider. A new crate needs an independent reason to exist, such as a dependency direction the graph must enforce, a compile-time boundary, or an independent lifecycle; a tidy name is not a reason. A new module needs a present artifact, and a directory is never created before its first real file.

A trait exists for generic programming, trait objects, or an extension, not to organize code. A fixed set of types known at compile time is an enum, and concrete types come before generics, generics before dyn. A macro is for what functions, generics, and traits cannot do. An object created only to run one action is a function in the outward API; a private context struct is fine. A trait with a single implementation is justified when it protects a real dependency direction or is stored as a trait object, as the probe trait is; a trait created to mock internal choreography is a collapse candidate. A one-use helper survives when it uniquely carries a protocol or ownership rule, such as the request-id grammar or the secret-key predicate, not when it shortens a call site. Modules named util, common, or helpers have no owner and are rejected by name.

Parallel execution paths, compatibility shims, and stale surfaces are collapse candidates unless an accepted current requirement keeps them with one owner, an observable activation, and a removal condition. Before keeping a new type, loop, check, or error classification, search the workspace for code that already owns that responsibility and extend or move that owner instead of adding a second copy; SQLSTATE and transient-error classification, for instance, already live in infra_postgres's sqlstate and transient. Structure follows the same reuse rule as code: a maintained crate that owns a general mechanism replaces template-owned code once it meets the requirement, and the dependency skill records that choice.

Trace one realistic change and ask whether the pieces it touches should change together. Pieces that should are a hidden link when nothing connects them: a copied value or rule, a call order callers must know, state one module sets and another reads. An exhaustive match or a required field already connects copies through a compile error, so that copy costs an extra edit rather than silent divergence; judge it by that cost. Keep the rule with its owner, or make the compiler or a test report the link; when no existing crate may own it under the crate graph, a named copy is cheaper than a new crate made to hold it. Pieces that should not change together are a needless link: a caller depending on internals, a general function with a parameter only one workflow understands, an interface that changes whenever its internals do, a stable crate importing a more volatile one. Cut it with privacy, a narrower signature, or a moved decision before adding a layer. Repeated text with independent reasons to change stays separate.

Code that exists for one situation is a requirement the design has not absorbed: a branch on one value or name, a parameter for one caller, a discarded error, a sleep or retry, a disabled test. Treat each as a search signal rather than a defect. Several may share one cause, and repairing that cause removes them together, while patching each leaves the cause to produce the next. Keep a case that states a real external condition or accepted policy, such as backoff during a dependency outage or a test ignored, with its reason, for an environment the suite cannot provide.

Keep the interface small: everything observable will be relied on, so items stay private until a caller needs them and each is reachable through one path. Filenames name the owned behavior rather than chronology or size, and files split by independent lifecycle, audience, or authority. Tests live beside their owner; the service crate's integration tests hold only black-box process proof.

For analysis or review, make no edits; try to delete or collapse each candidate and retain it only when removal would violate a current constraint or increase complexity. A named smell alone is not a defect, and a review need not manufacture findings. For implementation, select the least structure that owns the current responsibility, simulate one realistic next change to confirm it touches fewer owners with the structure than without, and preserve behavior, failures, ordering, and resource lifetime through any refactoring.
