# Rust Structural Quality

**Deletion test.** Judge a structure by the responsibility it owns and the facts a reader or caller must coordinate. Keep it when its interface makes that responsibility easier to understand, preserve, or change; collapse it when it only relocates the same reasoning. Honor supplied requirements and preserve settled choices outside the requested change; resolve only what the task leaves open.

Use the current project's ownership and dependency boundaries. In this service, the [repository architecture](../../../docs/repo-architecture.md) names the composition, leaf, provider, and feature owners. A standalone program does not need that crate layout. A new crate needs a present reason such as dependency direction, a compile-time boundary, or an independent lifecycle; a tidy name is insufficient. Split modules by coherent responsibility or authority, not an arbitrary size threshold. Create a directory only when its first real artifact needs it.

A trait serves actual variation, generic programming, an erased consumer, or an extension. It is not needed merely to organize code. Choose a concrete type for fixed behavior, an enum for closed alternatives, generics for required static variation, and dyn for a consumer needing erasure or heterogeneity. Account for API, code-size, and compilation constraints; these mechanisms are not a universal quality ranking. Prefer an existing standard trait when its contract fits. A custom trait that only enables mocking internal choreography is a collapse candidate. A macro must earn the work that functions, generics, or traits would otherwise own.

A private function used once is justified when its name, inputs, result, and failure behavior express a complete decision that the caller can understand without reading its mechanics. Validation or transformation can be such a responsibility. Keep trivial forwarding and fragments tied to a caller's local state inline. A meaningful receiver makes an operation a method; an object created only to invoke one action usually exposes a function instead, while a private context struct may still clarify ownership. The [responsibility examples](references/responsibility.md) distinguish useful factoring and dependency boundaries from extra indirection. Names such as manager, service, or helpers invite an ownership check; they do not establish a defect by themselves.

Trace one realistic change. Pieces that must change together form a hidden link when their relationship is only a copied rule, an undocumented call order, or state written and interpreted in separate places. Keep that rule with one owner, or make the compiler or an appropriate test expose the relationship. In this service, when the crates sharing such a rule have no common owner, that owner is `crates/shared-rules`, under the membership test in its crate documentation. An exhaustive match already makes a new variant visible, so repeating its cases is not equivalent to a silent policy copy. Similar text with independent reasons to change can remain separate. A shared abstraction that accumulates flags prompts a check for diverging responsibilities, rather than automatic extraction or deletion.

Cut unnecessary links before adding layers: use privacy, a narrower parameter or result, or a moved decision when a caller depends on internals or an interface changes with unrelated workflows. Search for the existing owner before adding another loop, error classifier, configuration source, or adapter. Compare a maintained general mechanism against custom coordination and failure handling when that choice is open. Neither fewer dependencies nor fewer files alone establishes simplicity. Avoid speculative capabilities, while recognizing reduced present comprehension and change cost as a valid benefit.

Keep unnecessary observable surface small. A public API creates compatibility obligations; do not add duplicate user-facing paths without a consumer reason. Internal re-exports and a deliberate facade can organize a crate without creating competing public APIs. Retain parallel paths, compatibility shims, or fallbacks only for an accepted current need with an owner, observable selection, and a removal condition. Before deleting a check, adapter, staging area, or recovery branch, name the behavior it preserves and where that behavior will remain. Removing a container that provides rollback, or a wrapper that preserves a required error response, is not simplification of the complete operation.

For analysis or review, make no edits. Show a requirement violation or a concrete maintenance consequence; line count, naming taste, and syntax preference alone are not blocking findings. For implementation, choose the least structure that owns the current responsibility, inspect its actual consumer, and preserve behavior, failures, ordering, atomicity, and resource lifetime. Use the existing validation boundary rather than adding a new framework, test seam, or proof gate to justify the structure.
