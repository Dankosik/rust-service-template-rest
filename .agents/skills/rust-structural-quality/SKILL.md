# Rust Structural Quality

**Deletion test.** Judge each added structure by the guarantee it owns and the facts callers must coordinate. Keep it when it makes that guarantee easier to establish or change; try removing it when it only relocates the same reasoning. Honor supplied requirements and preserve settled choices outside the requested change; resolve only what the task leaves open.

Use the current project's ownership boundaries. In this service, the crate graph is the dependency rule: the service crate composes; the config, health, and infra crates are leaves that never import one another's policy; feature crates depend on no transport or provider. A standalone program does not need that crate layout. A new crate needs an independent reason to exist, such as a dependency direction, a compile-time boundary, or an independent lifecycle; a tidy name is not a reason. A new module needs a present artifact, and a directory is never created before its first real file.

A trait needs a required variation or dependency constraint: generic programming, trait objects, or an extension, not code organization. Use an enum when callers must distinguish closed alternatives, a concrete type for fixed behavior, generics for actual static variation, and dyn for an erased or heterogeneous consumer. Choose by the caller and cost constraints; those spellings are not a quality ranking. A macro is for what functions, generics, and traits cannot do. An object created only to run one action is a function in the outward API; a private context struct is fine. Inspect the actual consumer to see how it meets that need; existing dyn usage alone does not justify erasure or a trait. A trait created only to mock internal choreography is a collapse candidate. A private function used once is justified when its name, inputs, result, and failure behavior let the caller understand a complete decision without reading its mechanics. Validation and transformation of a collection can be such a responsibility. Keep trivial forwarding and fragments that require the caller's local state inline. Extraction should reduce the facts understood together, without adding a wrapper type, trait, or module solely for separation. For borrowing-driven factoring or an uncertain trait boundary, read the [responsibility examples](references/responsibility.md). Names such as util, common, helpers, or manager prompt an ownership check; a name alone neither proves nor disproves cohesion.

Parallel execution paths, compatibility shims, and stale surfaces are collapse candidates unless an accepted current requirement keeps them with one owner, an observable activation, and a removal condition. Before keeping a new type, loop, check, or error classification, search the workspace for code that already owns that responsibility and extend or move that owner instead of adding a second copy; this service's SQLSTATE and transient-error classification, for instance, live in infra_postgres's sqlstate and transient. Structure follows the same reuse rule as code: a maintained crate that owns a general mechanism replaces template-owned code once it meets the requirement, and the dependency skill records that choice.

Trace one realistic change and ask whether the pieces it touches should change together. Pieces that should are a hidden link when nothing connects them: a copied value or rule, a call order callers must know, state one module sets and another reads. An exhaustive match or a required field already connects copies through a compile error, so that copy costs an extra edit rather than silent divergence; judge it by that cost. Keep the rule with its owner, or make the compiler or a test report the link; when no existing crate may own it under the crate graph, a named copy is cheaper than a new crate made to hold it. Pieces that should not change together are a needless link: a caller depending on internals, a general function with a parameter only one workflow understands, an interface that changes whenever its internals do, a stable crate importing a more volatile one. Cut it with privacy, a narrower signature, or a moved decision before adding a layer. Repeated text with independent reasons to change stays separate.

A branch on one value, a caller-specific parameter, a discarded error, a sleep or retry, or a disabled test prompts an ownership check. Establish the accepted condition it serves before judging it as a patch or a defect. Several may share one cause, and repairing that cause removes them together, while patching each leaves the cause to produce the next. Keep a case that states a real external condition or accepted policy, such as backoff during a dependency outage or a test ignored, with its reason, for an environment the suite cannot provide.

Keep the interface small: everything observable will be relied on, so items stay private until a caller needs them and each is reachable through one path. Filenames name the owned behavior rather than chronology or size, and files split by independent lifecycle, audience, or authority. Tests live beside their owner; the service crate's integration tests hold only black-box process proof.

For analysis or review, make no edits; try to delete or collapse each candidate and retain it only when removal would violate a current constraint or increase complexity. Before deleting a check, adapter, or recovery branch, identify its required behavior and where that behavior will be preserved. Show a violated requirement or concrete maintenance consequence; absent an explicit project rule, a name, line count, or syntax preference alone is not a blocking finding. For implementation, select the least structure that owns the current responsibility, trace one relevant change through the proposed owners to expose duplicated policy or unnecessary coordination, and preserve behavior, failures, ordering, and resource lifetime through any refactoring.
