# Introspection cache mechanism evidence

Status: ready as supporting Technical Design research, 2026-09-25. Scope is the corrected [R7/R9](../spec.md#r7-introspection-classification-and-capacity), not a new cache framework or standalone Research phase. Current adapter inspection is production `a896e21` plus disjoint mechanical cleanup; [system design](../design/system.md#optional-introspection-cache) owns the selected mechanism and values.

## Candidates and decision

The workspace already declares and locks Moka 0.12.16. The [registry](https://crates.io/crates/moka/0.12.16) reports that as latest stable, released 2026-08-09; registry API was read directly on this date. The maintained [upstream repository](https://github.com/moka-rs/moka) documents concurrent sync/async variants, weighted capacity, fixed TTL, per-entry expiry and no dedicated background threads since v0.12. Its [resolved future-cache API](https://docs.rs/moka/0.12.16/moka/future/struct.Cache.html), corroborated in installed `src/future/cache.rs:34–38`, explicitly describes capacity bounding as best effort. Expiry and per-entry policy can express non-sliding retention; trust isolation, claim revalidation and secret redaction still belong to the adapter. No upgrade is needed to evaluate it. Existing platform caveats and eviction scheduling are documented upstream; this is not a claim of an exhaustive vulnerability audit.

Moka is a suitable maintained alternative if approximate eviction capacity and its richer concurrent admission are desired. R7 does not demand a particular eviction policy or optimal hit rate, and no measured throughput target exists. For this small opt-in store, a checked std HashMap insertion under a short try-lock gives a direct finite count with no asynchronous eviction bookkeeping. Maintaining a strict admission gate alongside Moka would retain the adapter coordination while adding an otherwise unused dependency edge; choosing Moka without that gate would require reasoning about its retained pending/eviction state. Neither is justified by the current requirements. This is a local simplicity choice, not a claim that all valid caches require exact capacity or that Moka is unsafe.

The selected standard-library mechanism uses [HashMap](https://doc.rust-lang.org/std/collections/struct.HashMap.html) randomized hashing, lookup, retain and insertion; [Mutex::try_lock](https://doc.rust-lang.org/std/sync/struct.Mutex.html#method.try_lock) avoids waiting and exposes contention/poisoning as cache bypass. Only auth-specific admission/expiry/evidence rules are template-owned. No LRU, generic expiration engine, spawned work, new module or dependency is introduced. Existing secrecy stores the token key privately. A live concurrent entry is not overwritten; full or busy storage declines new retention while still returning the provider-verified outcome.

## Current owner evidence and costs

CodeGraph identified existing IntrospectionOptions callers in bootstrap, introspection preparation and mounted fixtures; changed source slices were then read directly because the index reported drift. `introspection.rs::verify_evidence` already owns request reserve, immediate semaphore admission, provider POST and typed validation. `claims.rs::validate_introspection_claims` owns active classification and the 30-second exp/nbf policy; it currently discards nbf after creating Principal. `lib.rs::Principal` owns redacted identity and normalized Vec<String> scopes. The cache therefore stays in introspection.rs, with private verified temporal evidence kept by claims.rs and optional private retained-buffer accounting beside Principal. Config and bootstrap retain their existing representation/conversion responsibilities. These are refinements inside established owners, not a new ownership panel trigger.

Default 256 entries and 30-second retention, bounded by 1024 entries and five minutes, are conservative design choices with no performance claim. Per-entry retained variable allocations are capped at 64 KiB to avoid multiplying the existing 1 MiB provider-body ceiling into large cache retention. Oversized valid evidence bypasses storage rather than changing token acceptance. Costs accepted: full-cache and contention misses may make extra provider calls; valid cached positives can hide revocation/outage until fixed expiry; expired allocations may persist until bounded opportunistic cleanup or verifier drop. Configurable TTL never outlives exp. Separate verifier instances deliberately do not share cache entries.

Reopen this choice only if a measured workload requires better concurrency or replacement hit rate, shared trust contexts/hot credential updates become required, or the direct bounded implementation becomes materially more complex than a supported maintained alternative. Executor-owned local fixture and controlled-clock proof will verify semantics; this supporting research does not claim runtime results.
