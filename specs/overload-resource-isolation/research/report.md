## 1. Что именно ограничивается

- **A — активная работа:** занятые permits, соединения, job slots или delivery slots.
- **W — ожидающие:** futures, которые ещё не начали работу, но сохраняют request/token/body/контекст.
- **B — внутренняя очередь:** очередь SDK, транспорта, executor или broker.
- **G — общий предел:** scope одного владельца, процесса, durable, базы или всех replicas.

Ограничение A не ограничивает автоматически W; ограниченный B не ограничивает число senders, ожидающих место. Время ожидания не ограничивает его численность без ограничения входного потока. Размер элемента не равен размеру всех удерживаемых объектов. `Arc<Semaphore>` разделяется между клонами одного владельца, но не между независимо созданными клиентами и replicas.

## 3. Middleware, deadlines, fairness и восстановление

### Ingress

HTTP, снаружи внутрь: request-id/response headers → observation → **admission** → error mapping → immutable RequestDeadline → timeout → panic catch → body limits → route authentication → idempotency/webhook policy → handler. Routing/fallbacks проходят harden. Поэтому очередь auth/SQLx удерживает HTTP permit; переполнение не исполняет handler. Probes пропускают semaphore, но socket cap остаётся.

gRPC: observation → **opening deadline → authentication → business admission → tonic handler**; затем observation забирает permit в terminal response owner. Один slow JWKS refresh способен породить много auth waiters, которые не входят в 256 business slots. Это реальный разрыв count accounting, хотя каждого ограничивает opening deadline. Health Watch также вне business cap и может быть долгоживущим. Message decode default 4 MiB, encode default `usize::MAX`; это per-message политика сгенерированного Tonic service, не HTTP body limit и не предел суммарного streaming payload. [Generated API](../../../crates/grpc-contracts/src/generated/example.v1.rs), строки 313–327.

HTTP timeout и permit заканчиваются до response-body EOF. Active gauge, наоборот, следует body lifetime, а duration/access-log записываются по headers. Поэтому `http_server_active_requests > max_in_flight` не доказывает поломку semaphore, а быстрый header p99 не доказывает быстрый complete-body p99. [Observation](../../../crates/infra-http/src/observe.rs), 58–119, 219–270.

gRPC server сохраняет caller deadline через DATA/trailers, в том числе независимым timer при неполлируемом flow-controlled body. Без `grpc-timeout` configured 8s — opening bound; намеренно долгий stream может удерживать весь business cap. Нельзя автоматически распространить 8s на все streams без изменения принятого контракта.

### PostgreSQL

SQLx acquire FIFO и cancellation освобождают waiter/permit ownership; очередь не имеет service-local W ceiling. Timeout/drop выполняемой операции не означает, что PostgreSQL немедленно остановил её или что COMMIT не состоялся. В этом SHA **уже закрыт** ранее опасный безграничный native return: [vendor patch](../../../vendor/sqlx-core/PATCHES.md), [connection](../../../vendor/sqlx-core/src/pool/connection.rs) 144–165 ограничивают целиком return callback/ping/close пятью секундами. Это освобождает локальную capacity даже при молчащей сети, но не устанавливает remote durable outcome.

Acquisition 3s + один statement до 8s не помещаются целиком в default HTTP 8s; outer timeout прервёт client future. Server statement timeout не равен client/network deadline и не ограничивает всю последовательность statements. `in_tx` не получает RequestDeadline. Контрпример чрезмерно широкой критике: idempotency и webhook ingress уже используют `postgres_attempt_end(RequestDeadline−100ms)` и outer bounded attempt; [helper](../../../crates/infra-http/src/harden.rs) 66–75, [idempotency](../../../crates/infra-http/src/idempotency/execute.rs) 151–180, [webhooks](../../../crates/infra-http/src/webhooks.rs) 137–146. Их не надо заменять вторым timer или retries.

Readiness сознательно использует тот же pool: saturation может снять **всю replica** с маршрутизации; recovery — следующий успешный refresh. Это ограничивает приток только там, где внешний balancer соблюдает readiness; прямой listener автоматически не прекращает бизнес-вызовы от cached not-ready. Liveness остаётся отдельной. [Probe](../../../crates/infra-postgres/src/probe.rs), 1–7, 32–36. Поведение balancer/production здесь не исследовано.

### Auth и provider work

Inbound default uncached introspection fail-fast ограничивает actual provider exchanges 32, а включённый cache допускает много same-token followers без provider permits. JWT unknown-key refresh также coalesces followers. В HTTP они способны занять все ingress slots одним медленным заполнением; в gRPC остаются перед business cap. Shared verifier означает конкуренцию HTTP/gRPC за provider/key cache. [Introspection](../../../crates/infra-bearerauthn/src/introspection.rs), 126–175, 190–218; [refresh](../../../crates/infra-bearerauthn/src/refresh.rs), 77–123, 182–208.

Outbound OAuth cold-token mutex FIFO; cancellation теряет очередь конкретного caller, не leader. Fetch cap 5s начинается после lock; caller deadline включает ожидание. Background refresh делит тот же lock и provider cap, с wake channel=1 и retry spacing 30s; это ограничивает trigger backlog, а не гарантирует refresh priority. Cache может продолжать обслуживать reusable token при failure. [OAuth](../../../crates/infra-oauth2-client-credentials/src/lib.rs), 638–700, 763–809, 908–1010.

Cache capacity — retention accounting: Moka best-effort; in-flight initializers/followers и retained principals вне cache entry count. Introspection default capacity256/TTL30s при включении; payload больше64 KiB не удерживается, но caller получает его. Exchange cache учитывает Bearer-header bytes до16 MiB и default1024 entries, но metadata/live references остаются вне этого веса. Не переводить эти значения в обещание heap ceiling.

### Исходящий HTTP после OAuth и webhook delivery

`infra-outbound-http::Client::execute` ограничивает **полный buffered exchange**, включая DNS/TLS/connect, headers, все body bytes и EOF, тем же caller absolute deadline и меньшим `Limits::operation_timeout`. Все три Limits обязательны: duration, response header count, response body bytes. HTTP/1 parser также имеет library buffer ceiling417792 bytes; idle pool timeout30s ограничивает retention, а не active count. Собственного semaphore/caller queue нет: active work принадлежит ingress/job/конкретному consuming class. Buffered payload ceiling L ограничивает accumulator, при moving growth временно запрашивается до2L; allocator/frame/header/retained result storage вне этого числа. [Client](../../../crates/infra-outbound-http/src/lib.rs), 42–47, 178–256, 284–314; [guide](../../../docs/outbound-http.md), 41–49.

OAuth `execute` сначала делает `authorize`, затем `self.resource.execute(request, deadline)` с **исходным** deadline. Token-provider permit уже не охватывает resource HTTP exchange; cache hit вообще может обходить token fetch. Поэтому cached credentials + медленный business provider способны занять все consuming HTTP/job slots при почти нулевой нагрузке на IdP. Ошибки token acquisition не dispatch ресурс; completed401/403 не replay,401 инвалидирует token для следующего caller. Внутренний Hyper-util retry только unsent request после отказа reused connection: не unlimited application replay; overall deadline остаётся. [OAuth resource dispatch](../../../crates/infra-oauth2-client-credentials/src/lib.rs), 837–870.

Outbound webhook `Dispatcher::register(max_concurrent)` уже отображает optional cap в jobs `Policy::max_running`. Delivery job использует `job.deadline()` в bounded client; HTTP timeout30s, response64 KiB/64 headers, policy20 attempts. Чтение до EOF заканчивается перед classification; все endpoints делят один kind `webhooks.deliver`, per-endpoint fairness отсутствует. Slow recipient с cap=None может занять все ordinary slots, но не dedicated outbox slot; cap и job retry mechanisms уже готовы, новый HTTP scheduler не нужен. [Webhook delivery](../../../crates/infra-webhooks/src/outbound.rs), 26–49, 185–205, 256–257. Эту finite buffered-HTTP границу следует сохранить; S3 streaming имеет иной lifetime contract.

### Jobs / JetStream / S3 / executor

Jobs FIFO-like `not_before,id` плюс `SKIP LOCKED` не обещают fairness по kind/tenant; optional `max_running` защищает другие kinds только если его выбрали. Slots удерживаются до durable outcome, включая outcome-write retries. Handler timeout60s, lease timeout+60s, local custody timeout+58s от claim send; после timeout кооперативная grace100ms, затем drop future. Outcome-write backstop12s/retry1s может удерживать slot до custody конца. Просроченный lease допускает fenced reclaim; retry backoff job не удерживает local slot. [Claim](../../../crates/infra-jobs/src/claim.rs), 258–272, 332–452, 552–556; [attempt](../../../crates/infra-jobs/src/attempt.rs), 262–359, 384–442.

Incoming webhook consumer держит PostgreSQL transaction на протяжении `process()`; документация запрещает делать здесь внешнюю медленную работу и предлагает durable job вместо неё. Все endpoints используют kind `webhooks.process`, поэтому per-kind cap не делит endpoints. [Consumer boundary](../../../crates/infra-webhooks/src/inbound.rs), 561–573, 700–708.

Dedicated outbox slot и worker отдельным процессом дают useful isolation. Но worker pool minima N+2, N+5 с outbox, 3 для outbox-only — это арифметическая ёмкость, **не reservation** против произвольного handler, берущего несколько соединений, JetStream consumer или maintenance. Worker также держит dedicated LISTEN session вне pool. API и worker pools разделены по процессам; база, CPU/IO хоста и provider quotas могут оставаться общими.

JetStream тянет только free delivery slots, не использует неконтролируемый consume prefetch. Slot включает handler+settlement. Handler30s, AckWait41s, retry delays1/5/30/120s, пятый failure отправляется в DLQ; max_deliver=-1 позволяет позже повторить settlement/DLQ. Неудачный DLQ publish оставляет source custody и redelivery30s. Consumer identity outage повторяется с backoff1s, а deleted/replaced durable является terminal error и останавливает worker — это contract protection, не автоматическое восстановление без рестарта для любых причин. [Consumer](../../../crates/infra-messaging/src/consumer.rs), 28–57, 199–212, 497–554; [guide](../../../docs/durable-messaging.md), 132–186.

SDK `send_publish` сначала ждёт max-ACK permit (default backpressure=true), затем command channel. Adapter ограничивает весь publish+ACK remaining deadline/5s. После передачи command cancellation не доказывает отсутствие dispatch; возвращается ambiguous, outbox сохраняет publication identity. В Tonic Buffer cancelled messages фильтруются worker перед dispatch при его polling; это не обещает немедленного освобождения queued storage и не отменяет уже отправленный RPC. Primary SDK source: async-nats0.50.0 `src/jetstream/context.rs:179–188,483–549`; Tower0.5.3 `src/buffer/worker.rs:67–101`, `service.rs:97–123`.

S3 GET SDK operation timeout охватывает request до returned output, **не чтение streaming body после `send()`**. SDK stalled-stream protection помогает при provider stall, но не заменяет reader lifetime policy. `Download` не имеет absolute lifetime timer; retained/unpolled body удерживает все storage slots до drop. `Download::bytes` освобождает slot после EOF, а bytes могут удерживаться дальше. PUT payload также может быть создан caller до storage admission. Presigned URL уже доступен и снимает relay workload с сервиса. [Download](../../../crates/infra-object-storage/src/download.rs), 14–25, 93–150; [AWS timeout contract](https://docs.aws.amazon.com/sdk-for-rust/latest/dg/timeouts.html).

Tokio timeout работает при polling/cooperative scheduling. CPU-heavy/non-yielding handler или синхронный stdout способен задержать timeout, probes и recovery. Прямой template-owned `spawn_blocking` найден для telemetry shutdown; business CPU executor пока не реализован. Shared blocking pool также используется библиотеками для DNS/FS. Его default512 ограничивает threads, очередь остаётся без backpressure; `shutdown_timeout` прекращает ожидание, **не убивает running closure**. [Runtime](../../../crates/service/src/bootstrap/mod.rs), 162–178; [worker runtime](../../../crates/jobs-worker/src/lib.rs), 165–173; [logging at the researched revision](https://github.com/Dankosik/rust-service-template-rest/blob/5927ffbba351af2f7fb8635316bbfa4ae5b31da6/crates/infra-telemetry/src/logging/json.rs), 308–313; [Tokio Builder](https://docs.rs/tokio/1.53.1/tokio/runtime/struct.Builder.html), [spawn_blocking](https://docs.rs/tokio/1.53.1/tokio/task/fn.spawn_blocking.html).

## 4. Сценарии перегрузки и граница отказа

| Сценарий | Что займёт ресурсы | Сейчас отказ / recovery | Реальный пробел |
| --- | --- | --- | --- |
| Burst HTTP при занятом handler cap | 256 admitted futures | Следующий 503 сразу; RA1; освобождение permit позволяет следующий вызов | Нет fairness между routes/tenants; тяжёлый route может занять все business slots |
| Slow JWKS / cached introspection и много followers | HTTP slots либо pre-admission gRPC futures | Shared fetch bounded; callers timeout/drop; старые JWT keys сохраняются | Provider semaphore не считает followers; нет total preauth gRPC count |
| PostgreSQL slow statements/locks/network | Все pool slots плюс waiters, probe | Acquire timeout; readiness lost; native return ≤5s; reconnect и refresh | Другие DB routes и readiness делят отказ; W не ограничен сам по себе; remote outcome отдельно |
| Долгие gRPC streams без caller deadline | Все grpc business permits | Отказ новым RPC, health проходит; recovery после terminal/drop | Нет выбранной class split unary/stream; finite opening timeout не finite lifetime |
| Slow/unpolled S3 download | Все8 storage slots и response-body lifetime | Новые storage calls Busy; recovery после EOF/drop | GET total deadline отсутствует; HTTP cap уже освобождён; HeadBucket probe проходит, storage при этом Busy |
| Slow kind / webhook endpoint | Все ordinary job slots; возможны Pg transactions | Timeout/retry/lease reclaim, outbox slot остаётся | Per-kind cap default none; endpoints одного kind не изолированы; Pg/CPU reservation нет |
| Cached outbound OAuth + slow resource HTTP / webhook recipient | Consuming ingress/job slots и bounded response accumulators; token cap не охватывает resource work | Full-body HTTP deadline/size refusal; webhook delivery retries через jobs | Active resource cap зависит от consuming class; optional delivery cap не установлен автоматически; per-endpoint fairness нет |
| Broker outage / DLQ full | Outbox retries, consumer settlement, durable backlog | Backoff/reconnect; identity mismatch terminal | Global backlog/retention/MaxAckPending зависит от operator; local C не ограничивает broker disk |
| CPU/non-yielding/blocking flood | Async workers или shared blocking threads/queue | Timers не являются preemption; caller timeout не останавливает blocking closure | Нет workload CPU admission; lowering max_blocking_threads лишь перемещает работу в очередь |
| Scale-out R replicas | R independent ingress/pool/provider/job caps | Local shedding сохраняется | Нет fleet allocator; autoscaling может перегрузить общую БД/IdP/S3; balancer fairness не проверена |

Все сценарии являются causal inference, не результатом нагрузочного опыта. Slow dependency может затронуть весь соответствующий класс и снять replica через dependency readiness; это не доказывает, что любой отказ уничтожит все независимые routes. API/worker процессы, probe bypass, default uncached introspection и отдельный outbox slot — существенные контрпримеры уже существующей изоляции.

## 6. Минимальный механизм

1. **Сначала замкнуть уже имеющиеся границы.** Для gRPC добавить дешёвый общий business-opening admission перед auth, сохранив terminal-stream cap и health exemptions. Это отдельный короткий permit до headers; перенести существующий business cap наружу проще, но тогда unauthenticated callers конкурируют с долгими authenticated streams — этот tradeoff надо решить в scoped design. Не менять статусы отказа и публичные probes.
2. **Ввести изоляцию только подтверждённого класса.** Медленные DB/provider calls или long streams получают один shared fail-fast permit у существующего owner; cache hits остаются вне provider attempt cap. OAuth token-provider cap не покрывает resource HTTP: если нужен bulkhead бизнес-зависимости, permit должен охватывать именно resource exchange через EOF, сохраняя existing complete-body Limits/original deadline. Outbound webhook сначала использует готовый `Dispatcher::register(max_concurrent)` вместо нового scheduler. Если цель — защитить быстрый/public путь от auth followers, нужен bound на all auth waiting work, а не только actual provider attempts. Никакой очереди по умолчанию.
3. **Finite HTTP/S3 relay должен иметь finite lifetime и retained-bytes owner.** Удерживать соответствующий class permit через body EOF/drop и применять accepted absolute/idle deadline; продуманно завершать stream без попытки заменить уже отправленный HTTP status. Долгие streams и presigned downloads получают отдельную политику. Глобальный HTTP body cap не механически расширять на все streaming responses.
4. **Для DB сохранить SQLx pool и return patch.** Перед expensive database class admission fail-fast, дальше native acquire под remaining parent deadline; сложные транзакции короткие, без внешних awaits. Не резервировать Pg соединение во время ожидания OAuth/S3. Existing 100ms response reserve переиспользовать там, где он уже владелец.
5. **Для jobs использовать `max_running` и отдельный outbox engine.** Если backlog имеет freshness/storage requirement, принять service-specific enqueue/expiry policy. На общем PostgreSQL строгий concurrent backlog cap должен быть атомарным под replicas; naïve `COUNT then INSERT` его не обеспечивает. Для delivery, который уже принят durable, expiry не означает молчаливое удаление обязательства.
6. **Перед новым CPU blocking work admission должен происходить до enqueue в executor.** Permit переместить внутрь closure и держать до actual completion; проверить expiry перед началом, передавать cooperative cancellation, не освобождать активный slot лишь по HTTP timeout. Для некооперативной длительной работы нельзя обещать recovery этим способом; нужен конкретный isolation/termination contract.

Это набор маленьких изменений у существующих владельцев, не общий admission framework. Не создавать их все сразу: первый полезный кандидат — preauth gRPC count + один подтверждённый экспериментом slow class. Числа class permits, queue depth и lifetime не выбираются без нагрузки.

## 8. Как измерить отказ и восстановление

Предложение следующему владельцу измерений; никакие сервисы/контейнеры/инфраструктура этим исследованием не запускались.

Один release build с тем же SHA/toolchain/lockfile; фиксированные profiles, CPU/memory limits, R replicas, DB/broker/provider settings. Генератор с заданным arrival rate, чтобы рост latency не уменьшал подаваемую нагрузку и не скрывал очередь. Снять healthy baseline, поднять arrival rate через saturation, удержать plateau несколько budget periods, отменить часть callers, убрать fault/уменьшить нагрузку и наблюдать recovery **с тем же PID/startup identity**. Время/длительность plateau выбрать из longest resource-custody budget; для jobs учесть lease и outcome-write tail, не лишь 60s handler.

| Нагрузочный опыт | Контроль | Результат, который отличит bound от иллюзии |
| --- | --- | --- |
| Mixed fast/slow HTTP + occupied DB | Cheap route без DB; медленные queries/lock; responsive DB отдельно от network blackhole | Successful fast-path p99; admit/refusal latency; pool waiters; readiness lost/recovered; RSS plateau |
| Auth followers | Same unknown kid или same uncached token с cache on/off; параллельно fast known-key/public calls | Provider requests bounded; all auth waiters bounded; cheap class сохраняет progress; zero post-expiry dispatch до handoff |
| Outbound resource HTTP | Warm OAuth cache, slow resource headers/body; webhook endpoints slow/fast с kind cap on/off | Token fetch count отделён от resource active count; complete-body timeout/bytes соблюдаются; unrelated routes/job kinds прогрессируют; retained result bytes не растут без budget |
| gRPC | Unary вместе с long streams; auth flood; callers с/без deadline; unread body | Distinct opening/lifetime counts; RESOURCE_EXHAUSTED latency; terminal/drop releases; preauth count |
| S3 | Held/unpolled Download; медленный HTTP reader; collecting bytes с retained responses | Slots возвращаются при принятой lifetime policy; complete-body time, byte budget; Busy; memory не растёт по duration |
| Jobs/outbox | Large backlog одного kind, max_running on/off; bad provider; exhausted Pg отдельно | Age по kind, ordinary/outbox progress, active/outcome slots, lease recovery и no duplicate committed effect |
| JetStream | C−active quota, брокер unavailable/reconnect, DLQ rejected, несколько replicas одного durable | Local envelope occupancy; durable pending/unacked; effective MaxAckPending; bounded retry rate; восстановление после transient outage |
| Blocking/CPU | Только когда появится реальный workload: медленные closures и expirations | Submitted/running/queued counts; closures не стартуют после expiry; slot живёт до completion; DNS/FS/probes не starving |
| R replicas | Тот же total arrival rate, затем одинаковый per-replica rate | Total DB connections/listeners/provider calls укладываются в fleet budget; лимиты не «исчезают» при scaling |

Нужные наблюдаемые величины: offered/admitted/rejected/completed/cancelled rate; rejection p50/p95/p99 отдельно от successful latency; queue count/bytes/oldest age/wait time; active counts по phase/class; RSS/live heap/CPU/Tokio queue and busy metrics; DB used/idle/max, locks/transaction age; durable backlog age, pending ACK/DLQ; время от снятия fault до первого успешного вызова и до стабильного baseline.

Уже есть HTTP shed/duration/active, gRPC shed/terminal metrics, DB occupancy и slow/acquire-timeout logs, auth/provider outcomes, job/delivery signals и Tokio reporter. **Не считать** HTTP active gauge числом admitted handlers или acquire latency числом waiters. Явных gauge для PostgreSQL/auth waiters и blocking admission/expiry нет; часть low-level Tokio queue detail требует `tokio_unstable`. Использовать существующие сигналы сначала; недостающий count получить bounded test instrumentation либо scoped production metric с bounded labels, без token/tenant IDs в labels.

Условия успеха задаёт сервис: memory ceiling с запасом, maximum refusal latency/wait age, допустимый fast-path p99 и recovery interval. Фальсификаторы универсальны: count/bytes растут с длительностью plateau; expired **ещё не отправленная** работа стартует позже; unrelated class теряет progress; slots не возвращаются после terminal/drop/completion; нужен restart после обычного снятия transient fault. Для durable/network side effects отдельно проверять known/unknown outcome — timeout не считать rollback.

## 9. Инварианты шаблона и параметры конкретного сервиса

**Безопасные инварианты шаблона:** конечные defaults и явная ответственность за отключение bounds; немедленный overload refusal с существующей Problem/Status identity; probes вне business slots; parent absolute deadline без reset; finite readiness/cleanup; единственный completion owner permits; finite fetch/prefetch count и bytes; отсутствие executor enqueue до admission; bounded logs/metrics labels; transient retries с backoff и durable identity; раскрытые scopes local/durable/fleet. Long-lived stream должен иметь явно выбранную политику, даже если она допускает отсутствие total deadline.

**Параметры сервиса:** K ingress/opening/stream/DB/provider/CPU по workload; Q и byte/age budgets, если ожидание необходимо; request/stream/operation SLO; decode/encode/retained-body limits; per-kind/tenant priorities; backlog freshness и правила expiry обязательств; max_workers/pools; broker retention/max_bytes/max_msgs/discard/MaxAckPending; sampling; число replicas и внешние quotas. Нельзя фиксировать default256 или32 как доказанный production safe value.

Fleet arithmetic: `Σ API pool maxima + Σ worker pool maxima + worker LISTEN sessions + migration/admin/pooler reserve ≤ available DB connection budget`; provider demand суммируется по независимо prepared owners и replicas. HTTP256 + gRPC256 — отдельные caps, не combined256, а preauth/health/stream work может лежать вне этой суммы. Broker durable MaxAckPending — shared unacked cap, **не** total pending-message/storage cap. Эти решения требуют effective configuration/readback; шаблон не должен добавлять distributed semaphore без настоящего fleet requirement.
