# Future evaluation protocol

Status: designed, execution deferred

This plan separates useful instruction content from examples, routing and
integrated work. It is part of the current deliverable, not permission to run
models or build an experiment. It makes no quality claim about the revised
skills. A later authorized evaluation freezes its actual budget, sample and
mechanism before execution.

## Conditions and claims

| Question | Conditions held apart | Inference limit |
| --- | --- | --- |
| Content | Same task receives no additional Rust skill package, complete frozen current package, or complete frozen revised package; an optional BeautifulRust reference is extra. Hold model/effort, common mandatory policy, source inputs, tools and budget fixed. | Supplied-package effect under that common context, not discoverability or universal quality. |
| Examples | Same revised principles with versus without example material; add an equal-information prose condition where feasible, with its own exact bytes. Keep selection fixed. | Examples versus additional explanation; differences cannot automatically be attributed to code formatting. |
| Routing | New positive, negative and overlapping tasks receive frozen catalogs. Allow no skill, one skill or several justified sets. | Missing/excess methods, decision coverage and selection/read cost; separate from implementation quality. |
| End-to-end | Normal bounded work with actual discovery, selected reference reads, tools, validation and continuation under the candidate system. | Integrated outcome; do not attribute an effect solely to body text. |

For the no-additional-package arm, mandatory policy remains common; report that
policy so the baseline is not called “no instructions.” Ensure common context
does not contain another arm's skill bodies or arm-dependent guidance through
AGENTS, automatic catalog discovery, global skills, memory, files or inherited
history. Freeze the common compatibility/binding text needed for fair local
work; report any unavoidable catalog or package exposure. A content condition
must supply its entire prespecified package rather than ask an agent to discover
it. Reference packages include their exact selected reference bytes; fixed
reference supply and permission for live retrieval are separate conditions.

## Exposure and run evidence

Before the later run, record protocol version, candidate and task source hashes,
common context, randomization, task allocation, effective model/effort, permitted
tools, validation scope, resource limits and recovery/stop rules. Fix what
counts as invalid, incomplete, infrastructure failure and authorized stop, and
what unavailable exposure evidence does to each claim. Do not change those
rules after viewing candidates.

Keep every started run, including refusal, interruption, timeout, malformed
output, setup failure and retries. Record supplied bytes and hashes separately
from transport acceptance, observed tool/file reads, final artifacts, terminal
status, timings and usage/cost. Native CLI text supplied to a process is not an
observable assembled model request. Unless a later tool actually exposes that
request, label it unavailable; do not infer hidden system context or retained
content. Truncation/compaction may invalidate continued-presence claims even
when initial supply is known. Receipt of bytes never proves cognition. Apply
the frozen rule to narrow or invalidate the affected comparison, retaining the
run; no selective omission or invented exposure pass.

Use isolated native sessions/checkouts only as required by the later accepted
mechanism. Clean history and controlled retrieval need evidence, not a prompt
claim. No run-control mechanism, evaluator or fixture suite is built now.

## Tasks and change cost

Keep development/pilot inputs separate from a closed confirmatory holdout,
frozen before candidate inspection. The earlier comparison reports and their
post-inspection probes are development leads only. The recommended future
8–12-task pilot calibrates protocol and rubrics; it does not establish broad
superiority or gate the current instruction rewrite. Choose holdout breadth
and repetitions later from decision precision, family variance and total cost.

Holdout families include modeling/parsing/identity/order; public-library API
and private application code; behavior-preserving edits; concurrency/lifetime;
durable outcomes/retry; integration/config/HTTP; diagnosis/measurement; and
simple tasks where added instruction should remain unnecessary. Include
multi-file changes, existing adequate solutions, user corrections and legitimate
authority/proof stops. Vary surface form so familiar examples do not determine
the answer.

For subsequent-change cost, fresh executors receive the anonymous changed
source and the same prespecified follow-up, without the original author's
reasoning. Measure correctness, affected owners/files only as diagnostics,
regressions, time and token cost; do not substitute line count for maintenance.
A resumed session is a distinct condition studying retained context, not
equivalent to a fresh executor. Plan cleanup and stop/recovery bounds before
effectful work. A justified scope or authority stop is not forced into a
failure score merely to reward completion.

## Assessment and report

Freeze task requirements, correctness checks, assessment rubric and acceptance
criteria before outputs are visible. Mechanical checks first establish only
their own behavior. Separate constraint correctness from assessor preferences
for clarity, idiomatic fit and justified complexity; a preferred style does
not erase a task violation. New adversarial probes discovered after inspection
are exploratory and can enter a later unseen holdout, not retroactively change
the frozen original verdict.

Use multiple independent blind judges with randomized candidate order. Give
them the task, baseline and anonymous artifacts, not arm labels, skill text,
author commentary or identifying execution logs. Retain ties, disagreement
and blinding limits, including recognizable code styles. Resolve material
correctness disagreements with anchored evidence; preserve taste disagreement
instead of forcing consensus. Judge a follow-up's result and original change
cost separately.

Report per-task and per-family outcomes, worst regressions, uncertainty,
infrastructure failures and all-started denominators alongside aggregate
preference. Repetitions are nested observations, not independent new tasks.
Show quality, completion, elapsed time, tokens/cost and exposure validity
separately. An average win cannot waive an accepted safety/contract regression.
The later protocol must fix practical decision thresholds and uncertainty
treatment before results; this design does not invent current model budgets
or sample counts to imply precision.

Refresh only affected claims after material model, harness/context delivery,
library or task-distribution change. Retain original protocols, artifacts and
receipts. A future finding can justify removing guidance as readily as adding
it. Current acceptance remains local instruction consistency, technically
checked examples and independent review.
