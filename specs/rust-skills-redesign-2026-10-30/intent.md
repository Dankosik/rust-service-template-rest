# Intent: make Rust skills improve engineering decisions

Status: ready

## Problem

The Rust skill system has useful methods, but it mixes transferable judgment,
library mechanisms and service-local policy. Several skills compete for the
same decisions, and the fixed prose format prevents concise code contrasts and
conditional references. Existing comparisons do not establish broad quality
improvement: optional loading confounded the first comparison, while the later
forced-content comparison had a narrow task set, one judge and an exploratory
post-inspection probe.

## Desired outcome

Implement the instruction-system recommendations in the accepted research
report as one coherent, maintainable system. Help a capable model choose
representations, preserve invariants, assign responsibility, own resource
lifetimes, justify abstractions
and verify observable behavior. Preserve the model's discretion and remove
instructions whose additional value is unsupported. Deliver the revised skills,
their routing and format controls, useful checked examples and a documented
future evaluation plan. Stop after the local system changes and their ordinary
mechanical verification and independent review. Comparative runs and a new
experimental runner are explicitly deferred.

## Affected actors and systems

Agents implementing and reviewing Rust changes; maintainers evolving the
template and derived services; the Rust skill catalog and its supporting
materials; canonical repository instruction owners, structural checks and
generated harness views; evaluation executors, blind assessors and evidence
consumers.

## Scope and non-goals

Local implementation, documentation, focused validation and independent reviews
in this repository. Use subagents for independent parallel responsibilities.
Preserve the existing
`specs/rust-skills-comparison-2026-10-30/` bundle and unrelated work.
No remote publication, merge, deployment, infrastructure change, purchase,
global agent configuration change or unrelated service-runtime redesign is
requested. Do not perform model/skill comparisons or build an experimental
runner, evaluator or new comparative fixture suites in this stage. BeautifulRust
is comparative evidence, not the definition of success. Ordinary implementation
and review subagents remain authorized; they are not experimental participants.

## Constraints

Quality means correctness, clarity, idiomatic use, justified simplicity and ease
of subsequent change within each task's requirements. Mandatory authority,
security, contract and release boundaries remain effective. Skills may guide
judgment but may not grant effects or create unrelated completion gates.
Design for a strong existing model rather than assume it needs generic Rust
instruction. Keep historical evidence intact and distinguish supplied content,
observed behavior, assessor preference and measured effects.

Technical decisions and task allocation belong to the agent system. Use
existing mechanisms and dependencies where adequate. The deferred evaluation
plan preserves separation of content, examples, selection and integrated work;
its live budget and run decisions are outside this stage and do not block the
instruction changes.

## Success signal

The revised instruction system and its controls agree; every current Rust
method has an explicit disposition and one understandable responsibility;
examples explain consequential choice boundaries; mandatory local rules retain
canonical owners. Mechanical checks and independent review close the local
change without a claim of measured improvement. The future evaluation plan
separates content from selection, includes no-additional-skill baselines,
compares examples independently, uses diverse unseen tasks and blind assessment,
and accounts for subsequent-change cost, failures, uncertainty and exposure
limits. No experiment or experimental infrastructure is needed to finish this
stage.
