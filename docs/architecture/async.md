# Async Architecture

Load for a change to the jobs pack: the job table or its statements, enqueue,
claiming, fencing, retries and backoff, retention, the worker process, or
their proof. Code and crate documentation remain the final factual authority;
this leaf records the mechanism and the decisions a later change should weigh
before reopening them. The adopter contract is the
[Background jobs](../background-jobs.md) guide.

## The job table and states

One table, `background_jobs`. One forward-only migration. No extension.
`gen_random_uuid()` is core since PostgreSQL 13, so the migration needs no
extension.

| Column | Type and bound | Why |
| --- | --- | --- |
| `id` | `uuid`, generated by the database; crosses SQL as text | The identifier a handler keys an effect on. A UUID stays unique across databases, so a provider key derived from it cannot collide between environments that share an account, or after a rebuild. Text at the boundary (`id::text`, `$n::uuid`) means sqlx needs no `uuid` feature, so every crate keeps the same sqlx features and the image compiles sqlx once. |
| `kind` | `text`, 1 to 64 of `[a-z0-9._-]`, first character `[a-z]`, validated in Rust | ASCII only, so no server encoding can reject it. |
| `payload` | `bytea`, at most 262 144 bytes, validated in Rust | The exact `serde_json` bytes. `jsonb` rejects `\u0000`, and `json` depends on the server encoding. Either would let a payload that passed validation abort the caller's transaction. Operators read it with `convert_from(payload, 'UTF8')`. |
| `unique_key` | `bytea`, 1 to 255 bytes of UTF-8 without control characters, or null | Same reason as `payload`: a key's characters can never be a database failure. |
| `state` | `text`, `CHECK` in `pending`, `running`, `completed`, `failed` | The four states, readable in SQL. A PostgreSQL enum would make a later value a harder forward migration. |
| `failure_reason` | `text`, `CHECK` in `permanent`, `exhausted`, null otherwise | The two terminal reasons, same migration argument. |
| `attempts` | `smallint`, at least 0, default 0 | Budget units used. No policy exceeds 25, so the value never needs a wider type. |
| `claim_generation` | `bigint`, default 0, from the sequence `background_jobs_claim_generation` | The fencing token. 0 means never claimed. `nextval` never hands a value out twice, even when the claim that drew it rolls back. |
| `not_before` | `timestamptz` | When the job may be claimed, on the database clock. |
| `claim_expires_at` | `timestamptz`, set exactly while `running` | The claim's expiry, on the database clock. |
| `finished_at` | `timestamptz`, set exactly while terminal | When the job became terminal. Retention counts from it. |
| `error_summary` | `text`, at most 1024 bytes | The latest failure's summary. The worker writes it. Enqueue never does. A non-UTF-8 database can fail that write; claim expiry then recovers the job inside the attempt budget. |
| `trace_context` | `text`, a W3C `traceparent` of 55 bytes, or null | Built by the engine from the current span, so it is always ASCII. |

Three `CHECK` constraints encode the state machine. No correct engine write
violates them. They catch engine defects in the database proof. They are not
input validation. That stays in Rust, where a typed error leaves the caller's
transaction usable.

- `background_jobs_claim_matches_state`:
  `(state = 'running') = (claim_expires_at IS NOT NULL)`.
- `background_jobs_reason_matches_state`:
  `(state = 'failed') = (failure_reason IS NOT NULL)`.
- `background_jobs_finished_matches_state`:
  `(state IN ('completed', 'failed')) = (finished_at IS NOT NULL)`.

The sequence `background_jobs_claim_generation` is `bigint` and is owned by
`background_jobs.claim_generation`.

Four partial indexes. Each serves one reader, and a stranded or terminal
population stays out of the others.

| Index | Shape | Serves |
| --- | --- | --- |
| `background_jobs_live_unique_key` | unique on `(kind, unique_key)` where the key is not null and `state` is `pending` or `running` | At most one live job per kind and key. A terminal job frees the key. |
| `background_jobs_pending` | `(kind, not_before, id)` where `state = 'pending'` | Claim order, per registered kind. |
| `background_jobs_running` | `(claim_expires_at)` where `state = 'running'` | Expired claims, and claim upkeep. |
| `background_jobs_terminal` | `(state, finished_at)` where `state` is `completed` or `failed` | Retention. |

| From | Trigger | To | `attempts` | `claim_generation` | Other columns |
| --- | --- | --- | --- | --- | --- |
| (none) | enqueue | `pending` | 0 | 0 | `not_before = now + delay` |
| `pending`, due, registered kind, budget left | claim | `running` | +1 | new | `claim_expires_at = now + 30 s` |
| `running` with an expired claim, budget left | claim | `running` | +1 | new | same |
| `pending` or expired `running`, `attempts` at or above the claiming worker's budget | claim | `failed` / `exhausted` | unchanged | new | `finished_at = now`, claim cleared, `error_summary` kept or set to `attempt budget spent` |
| `running`, current claim | extend | `running` | unchanged | unchanged | `claim_expires_at = now + 30 s` |
| `running`, current claim | success | `completed` | unchanged | unchanged | `finished_at = now`, claim cleared |
| `running`, current claim | retryable failure, budget left | `pending` | unchanged | unchanged | `not_before = now + backoff`, `error_summary`, claim cleared |
| `running`, current claim | retryable failure on the last unit | `failed` / `exhausted` | unchanged | unchanged | `finished_at`, `error_summary`, claim cleared |
| `running`, current claim | permanent failure | `failed` / `permanent` | unchanged | unchanged | `finished_at`, `error_summary`, claim cleared |
| `running`, current claim | release at the end of the drain | `pending` | -1 | unchanged | claim cleared; `not_before` unchanged, so the job is due at once and keeps its place in claim order |
| `completed` older than 24 h, or `failed` older than 7 days | retention | deleted | | | |

`now` is `statement_timestamp()` of the statement that writes. That is the
database clock. A worker's own timers use its monotonic clock. No decision
uses a worker's wall clock. Any outcome write whose claim is not current
changes nothing.

## Enqueue flows

Enqueue runs inside the caller's `in_tx`
([Transactions](persistence.md#transactions)). It is the only insert. It
accepts the shared opaque `&mut infra_postgres::Tx`, obtains its connection
inside the jobs adapter, and issues no transaction-control SQL, savepoint,
or second connection. A handler may pass the capability its own `in_tx`
closure receives, so a follow-up job commits with that handler's writes.

Validation runs before any statement. The kind name must match the grammar
above. A unique key, when set, must be 1 to 255 bytes of UTF-8 without
control characters. The delay defaults to zero, drops any sub-microsecond
part, and must be at most 36 500 days, so every accepted delay is a
representable timestamp. The payload must serialize as JSON of at most
262 144 bytes. A failure is a typed `EnqueueError` (`InvalidKind`,
`InvalidUniqueKey`, `InvalidDelay`, `Serialize`, `PayloadTooLarge`). Nothing
is sent, and the caller's transaction stays usable. The producer sets no
attempt budget and no timeout. Those are the kind's policy in the worker.

When the current span's context is valid, the engine captures
`00-{trace_id}-{span_id}-{flags:02x}`. No `tracestate`, no baggage. An
invalid context stores null.

One statement follows:

```sql
INSERT INTO background_jobs
    (kind, payload, unique_key, not_before, trace_context)
VALUES ($1, $2, $3, statement_timestamp() + $4, $5)
ON CONFLICT (kind, unique_key)
    WHERE unique_key IS NOT NULL
      AND state IN ('pending', 'running')
DO NOTHING
RETURNING id::text AS id
```

Payload and unique key bind as bytes. The delay binds as an interval of
whole microseconds. A returned row is `Created`. No row is `Duplicate`.
Without a key the partial index is not involved, and the row is always
written.

A database failure is `EnqueueError::Database`. The caller's transaction is
aborted, as for any failed statement. The caller classifies `40001` with
`infra_postgres::retryable`. There is no retry loop in the seam.

Commit fate is the caller's. Rollback and `CommitFailed` leave nothing.
After `CommitUnknown` the job exists exactly when the business write does,
and the caller reconciles against that write rather than retrying blindly.
No worker sees an uncommitted row. The claim reads committed rows only, in
its own transaction.

When an uncommitted transaction is writing the key's holder, enqueue waits
for it inside the session's statement budget, then the caller's isolation
decides. Those outcomes are PostgreSQL's own behavior for this statement
against the partial unique index. The guide records them in
[Enqueue in the transaction](../background-jobs.md#enqueue-in-the-transaction).

A unique key suppresses a second live enqueue. It does not make the
handler's effect idempotent, and a terminal job frees the key.
[Make effects idempotent](../background-jobs.md#make-effects-idempotent).

An idempotent operation uses the shared `infra-postgres::Tx` that
`infra_http::idempotency` re-exports. Its provider adapter calls
`infra_jobs::enqueue(tx, ..)`; the one READ COMMITTED transaction commits the
business write, success record, and job together, or none. Replay, refusal,
and an in-progress answer never run work and enqueue nothing. The jobs seam
does not acquire, commit, or roll back that transaction. [HTTP
idempotency](../http-idempotency.md) owns its request, retry, and response
rules.

## Claiming, fencing, and recovery

The transition table above is the state machine. This section is how a
worker moves a row, and how it proves what a write did.

### Operation bounds

Every statement except enqueue runs in its own explicit `READ COMMITTED`
transaction through `in_tx_with`
([Transactions](persistence.md#transactions)). An explicit level keeps a
stricter `default_transaction_isolation` from turning `SKIP LOCKED` claims
into serialization failures. Each of those statements, except the startup
check, runs under a 12 s client backstop: the 3 s acquire, the session
`statement_timeout` of 8 s, and 1 s
([Budgets](persistence.md#budgets)). The server normally ends the statement
first. The startup check has its own 5 s bound, from acquire through the
end of its transaction, and does not use that backstop.

An unknown commit, for every engine statement, means the statement returned
and no commit acknowledgement followed. That covers an unknown commit
outcome, a connection error during commit, and the backstop firing after the
statement returned. It is reported as `commit_unknown`, never as a timeout.
A commit the server rejected wrote nothing.

### Claim

The claim loop holds `jobs.max_workers` slot permits. On a 1 s tick
(`MissedTickBehavior::Delay`), or at once after a claim that filled every
requested slot, it takes the free slots, runs one claim for that limit, and
returns the slots it did not hand to a supervisor. A claim that returns
fewer jobs waits for the next tick. An idle worker therefore claims a job
that becomes available at time t by t + 1 s plus claim latency.

The statement reads, per registered kind, at most that many due `pending`
rows through a `LATERAL` lookup on `background_jobs_pending`, with
`FOR UPDATE SKIP LOCKED`, ordered by `not_before` then `id`. It also reads
expired `running` claims of those kinds from `background_jobs_running`, with
the same lock, order, and limit. It then keeps the earliest of that union,
again limited to the free slots, and updates those rows. A backlog of
another kind, or of a kind no running worker registers, costs nothing per
claim. Stranded jobs stay live until a worker that registers them runs.
Concurrent workers take disjoint jobs. Rows a lateral branch locks but does
not pick stay locked only until this short transaction commits.

The target is matched with `id = ANY (ARRAY(..))`, not by joining the
picked ids. The joined draft's generic plan scanned the whole table: 16 ms
at 110 250 rows, growing with retained history. The `ANY` form uses the
primary key, 0.1 ms on that table. sqlx reuses prepared statements, so
generic plans are the ones that matter.

Each claimed row draws `claim_generation` with
`nextval('background_jobs_claim_generation')`. A returned `running` row is
admitted. A row whose `attempts` are at or above the claiming worker's
budget becomes `failed` / `exhausted` in the same statement. Its summary is
kept, or set to `attempt budget spent` when it had none. No payload is
returned, no handler runs, the claim uses no further unit, and the claim
loop records `exhausted` itself. That row has no registry entry. It covers
a lost attempt that already spent the budget, and a worker that registers a
smaller budget than the attempts already used. The claiming worker's policy
governs that claim. Workers with different policies for one kind may run
at once.

When the claim's commit is unknown, the claim loop keeps the returned rows
outside the transaction and reconciles before it admits anything. A rejected
commit claimed nothing. A row that carries the generation this claim drew
was claimed. Any other row was not. Reconcile retries every 1 s until the
claim's local deadline, 28 s after the claim was sent, and each try takes
the engine permit for that statement only. A proven `failed` row is recorded
`exhausted` by the claim loop, with the summary the claim returned, and gets
no registry entry. A proven `running` row is admitted if its deadline has
not passed. Otherwise the claim loop records it `lost` with reason
`extension`, and claim expiry recovers it. Rows still unattributed at the
deadline are treated as not claimed.

There is no ordering guarantee between jobs beyond `not_before` then `id`.
No priorities, no named queues, and no per-kind concurrency limit.

### The fencing token

A claim is the pair `(id, claim_generation)` the claim statement returned.
Every write an attempt makes, extend, outcome, or release, carries both
values and `state = 'running'`. The claim is current while the row is
`running` with that generation. Expiry alone does not end it. An expired
claim that no later claim replaced still extends and still records. Only a
new claim sets the generation, and it draws a new value from the sequence.
No two claims ever carry the same token, including a claim that rolled back.

Two alternatives do not hold that property. Incrementing the previous value
would let a rolled-back claim's token come back on the next committed
claim, so a worker that reconciled an unknown commit could hold a token
another worker also holds. The attempts counter cannot serve either,
because a release gives its unit back and the counter then repeats. A stale
extension could then extend a newer claim and break the 30 s recovery bound.

### Recovery arithmetic

`CLAIM_TTL` is 30 s. The claim and each extension set
`claim_expires_at` to database now plus 30 s. A job whose worker stops
extending is claimable again exactly 30 s after its last executed extension,
on the database clock.

`UPKEEP_INTERVAL` is 10 s. One batched extension per worker. Results are
matched by the whole claim `(id, claim_generation)`, never by id alone,
because two claims of one job can be in flight in one worker. A claim the
statement does not return is superseded: that attempt is cancelled with
outcome `superseded` and writes nothing more. This statement hash-joins the
running-jobs index. The `ANY` form was slower here, which is why upkeep does
not use the claim statement's match.

`CANCEL_MARGIN` is 2 s. Before sending the claim or an extension, and after
the connection is acquired, the worker reads its monotonic clock (`t_sent`).
When the statement is acknowledged, each returned claim's local deadline
becomes `t_sent + 28 s`. The database executed that statement no earlier
than `t_sent`, so its expiry is at least `t_sent + 30 s`, and local
cancellation fires at least 2 s earlier. The margin covers timer lateness
and any monotonic-rate difference. An extension that fails, times out, or
returns an unknown commit does not move the deadline, which only makes
cancellation earlier than the database expiry.

Extensions run every 10 s, so after the last acknowledged extension a claim
gets two more tries, at about +10 s and +20 s, before the local deadline at
+28 s. A database outage shorter than about 18 s loses no claim. A claim
made just after an upkeep round waits at most 10 s for its first extension,
inside the 28 s. A worker that cannot extend cancels the attempt on that
local deadline and writes nothing. The next claim by any worker that
registers the kind takes the job, increments `attempts` (the lost attempt
used its unit), and draws a new generation. The handler may run again. Its
effect is idempotent by contract.

`POLL_INTERVAL` is 1 s. Pickup is that interval plus claim latency, and a
full claim is followed at once by another, as the claim loop above does.

A database clock that jumps forward can expire a claim early. That breaks
this arithmetic. The attribution below assumes it does not happen.

### Reconciliation

```sql
SELECT id::text AS id, claim_generation, state, attempts
FROM background_jobs
WHERE id = ANY ($1::uuid[])
FOR SHARE
```

It runs in its own `READ COMMITTED` transaction, after the write it
attributes. `FOR SHARE` waits for any transaction still writing those rows,
including one whose commit the client gave up on, and then reads the settled
row. A plain read would return the pre-commit row. The wait is bounded by
the session's 8 s `statement_timeout`. A timeout is a failed reconcile.

`attribute` maps a row to the attempt's claim:

| Row | Attribution | Recorded as |
| --- | --- | --- |
| Missing | `Superseded` | `superseded` |
| Another `claim_generation`, read before the local deadline | `Written` | this attempt's own write took effect, and a newer claim followed |
| Another `claim_generation`, read at or after the local deadline | `Superseded` | `superseded` |
| Same generation, `running` | `Unapplied` | the supervisor retries its write; the drain-end protocol records `lost` with reason `release` |
| Same generation, `pending`, `attempts = attempt - 1` | `Released` | `released` |
| Same generation, `completed`, `failed`, or `pending` with `attempts = attempt` | `Written` | the attempt's intended outcome |

A read before the local deadline means the result arrived before that
deadline. Database expiry is at least 2 s later, so no other claim could
have replaced a claim that was still `running`. A row that then carries
another generation proves that one of this attempt's own writes released
the row first: a retry, or the drain-end release.

The table is exhaustive. Only a claim sets `claim_generation`, and each
claim draws a value no other claim carries. While a row carries this
claim's generation, only this attempt changes its state: complete, retry,
fail, or the drain-end release. Retry keeps `attempts`. Release decrements
it. The two `pending` rows are told apart. Retention deletes only terminal
rows older than 24 h, far beyond an attempt's life.

Three uses, each immediately after the statement it attributes:

- A supervisor's outcome write that affected zero rows, or whose commit is
  unknown. It is attributed at once, not retried first.
- The drain-end release, for claims the release did not return, or for all
  of them when the release's commit is unknown.
- The claim loop, after a claim whose commit is unknown.

### The attempt registry

The registry holds one entry per admitted attempt, keyed by the claim
`(id, claim_generation)`, plus a closed flag. Both sit behind one mutex
that is never held across an await. Keying by the claim lets a re-claim of
the same job coexist with an older attempt that is still recording.

The entry is the right to record. Exactly one party takes it, with `take`
or `close`, and that party makes the one `record` call. Every other party
records nothing. `record` is the one emitter of the attempt counter, the
attempt records, and the duration histogram.

An outcome is recorded only when the database proves it, in one of three
ways: an acknowledged write that affected the row; a reconcile row
attributed as above; or an extension that did not return the claim while
the handler was still running. None of the attempt's own writes can have
run in that last case, so a newer claim holds the row.

An attempt nothing can attribute is `lost`. Reason `extension`: the local
deadline passed while the handler ran, or a claimed `running` row was past
its deadline before a handler started. Reason `record`: the outcome could
not be written and attributed before the deadline. Reason `release`: the
drain-end release could not be attributed. The job waits for claim expiry
with the unit used, unless one of its writes took effect unseen. In that
case the database already holds that outcome.

Only the claim loop admits. Admission spawns the supervisor and inserts the
entry in one lock hold. Each admitted attempt owns one slot permit, released
on every exit, abort included. A closed registry admits nothing. The claim
comes back, and the claim loop releases it with a deadline of now plus the
12 s backstop. The claim loop drops slot permits it took but did not hand
on: rows not claimed, budget-spent rows, and handed-back claims.

A handler starts only through the registry, and only before the local
deadline. No handler starts once `close` has taken the entry. If the
deadline has already passed, the supervisor records `lost` with reason
`extension` and does not start it. A payload that does not decode never
starts a handler. Handler tasks are spawned on their own, not on the
attempt tracker. The supervisor owns each one through its abort handle.
The drain waits for supervisors only.

When the handler completes, times out, or the payload does not decode, the
supervisor stores the intended outcome and the handler's run time. That
also stops extensions. It then writes complete, retry, or fail. If `close`
has already taken the entry, the supervisor sends no write and records
nothing. An attempt with no stored intended outcome therefore never wrote.

One row records the intended outcome. Zero rows, or an unknown commit,
reconciles at once. `Written` records the intended outcome. `Superseded`
records `superseded`. `Unapplied` retries the write after 1 s. Any other
failure, including a failed reconcile, retries after 1 s. Whatever is still
unresolved at the local deadline is `lost` with reason `record`. The
supervisor keeps its entry throughout, so the drain-end protocol can still
take it, and reconcile then attributes whichever write took effect.

Upkeep acknowledges or supersedes only an extending entry whose generation
matches. A supervisor whose handler has already ended ignores the
superseded signal. Its own write and reconcile decide.

| Who takes the entry | When | Records |
| --- | --- | --- |
| The supervisor | Its outcome write resolved; or its local deadline passed first; or the superseded signal fired while its handler ran | The resolved outcome; `lost` (`extension` while the handler ran, `record` after); `superseded` |
| The drain-end protocol | Every entry still present, in one `close` | `released`, the intended outcome, `superseded`, or `lost` with reason `release` |

### The drain-end protocol

`cancel_and_release` runs after a drain that ended early, and from
`shutdown::abort_startup` when the engine had started.

1. Stop claiming, then close the registry. Under one lock hold this sets
   the closed flag and takes every entry, and with them each attempt's
   right to record. Nothing further is admitted, and no handler starts.
2. For each taken entry, fire the handler's cancellation, then abort the
   handler, if it started, and its supervisor.
3. Release every collected claim in one statement. Each returned claim goes
   back to `pending`, its unit is given back, and its place in claim order
   is kept. A running claim always holds at least one unit, so the
   decrement is never negative.
4. Reconcile whatever the release did not return. When the release's commit
   is unknown, reconcile all of them. Record each attempt once.

The claim loop is never aborted. A claim that completes after the registry
closed finds it closed and releases its own claims the same way.

A returned claim is `released`. For every other attempt, the recorded
outcome is decided from the attribution (or none, if the attempt is still
unattributed when the deadline passes or a statement fails), whether the
row carried another generation, whether the release's commit is unknown,
and the intended outcome. A `lost` here always has reason `release`. The
table is exhaustive over those inputs. Two rows cannot happen; they stay
so a later change does not drop them and leave a hole.

| Attribution | Row's generation | Release | Intended outcome | Record |
| --- | --- | --- | --- | --- |
| `Released` | Any (`attribute` returns it only for this claim) | Any | Any | `released` |
| `Written` | This claim's | Any | Settled | The intended outcome |
| `Written` | This claim's | Any | None | `lost`. This cannot happen: an attempt with no intended outcome never wrote |
| `Written` | Another, read before the deadline | Known | Retry or timeout | The intended outcome. The release did not release this claim, so the supervisor's write did |
| `Written` | Another, read before the deadline | Known | None, or terminal | `superseded`. This cannot happen: neither write can have released the row |
| `Written` | Another, read before the deadline | Unknown | None, or terminal (`completed`, `permanent`, `exhausted`) | `released`. A terminal row is never claimed again, so only the release can have released it |
| `Written` | Another, read before the deadline | Unknown | Retry or timeout | The intended outcome. Either write may have released the row |
| `Superseded` | Any | Any | Any | `superseded` |
| `Unapplied`, or none | Any | Any | Any | `lost` |

Each failed statement is counted once, under `release` or `reconcile`. The
release and reconcile functions themselves observe nothing. Their caller
does.

### Permits

One engine permit serializes claim, extend, release, retention batches,
gauge samples, and the reconcile that the claim loop or the drain-end
release sends. At most one of these runs at a time. The permit is taken per
statement and is never held across a wait, a backoff, or admission. The
drain-end release holds it once, across its release and its reconcile.
Release and reconcile never take the permit themselves. Their caller holds
it.

A supervisor's outcome writes, and its reconcile, run in its own attempt
slot. They do not take the engine permit.

## Outcomes, backoff, and retention

### Outcome writes

From the handler's end, the attempt is not extended. While extensions are
being acknowledged, the last one was at most one upkeep interval ago, so
the outcome write has between 18 s and 28 s of the current claim left.

`rows_affected` of 1 means the write took effect. 0 means it changed
nothing, and the attempt reconciles at once, because an earlier try of the
same write may have committed with its acknowledgement lost. An unknown
commit reconciles at once as well, not after a retry.

| Attempt ends with | Write | Job becomes | Unit |
| --- | --- | --- | --- |
| Handler success | complete: `state = 'completed'`, `finished_at` set, claim cleared | `completed` | used |
| Retryable error, panic, timeout, or a payload that does not decode, budget left | retry: `pending`, `not_before = now + backoff`, summary stored, claim cleared | `pending` | used |
| The same, on the last unit | fail, reason `exhausted` | `failed` / `exhausted` | used |
| Permanent error | fail, reason `permanent` | `failed` / `permanent` | used |
| Cancellation at the end of the drain | release | `pending`, due at once, place kept | given back |
| Claim lost | none, if this attempt's writes did not take effect | unchanged by this attempt | as claimed |

A panic is caught, never ends the worker, and counts as a retryable error.
The guide states the same mapping in
[retries](../background-jobs.md#retries-failures-and-retention).

### Backoff

After the n-th used unit fails, n from 1 to 24, the job waits `n^4` seconds
times `p / 1000`. The 25th failure of a 25-unit budget is `exhausted` and
does not schedule a wait. `p` is deterministic per-job jitter in
900..=1100, plus or minus 10 percent, from splitmix64 of the job id
and the attempt:

```text
x = (high 64 bits of id) XOR (low 64 bits of id)
    XOR (n * 0x9E3779B97F4A7C15, wrapping)
z = (x ^ (x >> 30)) * 0xBF58476D1CE4E5B9
z = (z ^ (z >> 27)) * 0x94D049BB133111EB
z = z ^ (z >> 31)
p = 900 + z % 201
delay_ms = n^4 * 1000 * p / 1000
```

All arithmetic is `u64`, wrapping where marked. The largest term,
24^4 times 1000 times 1100, does not overflow. The delay is whole
milliseconds and binds as an interval added to the database clock. Jitter
is fixed for one job and one attempt. That spreads retries across jobs,
makes the arithmetic unit-provable, and needs no random-number dependency.
The 25-unit budget spans the sum of `n^4` for n from 1 to 24, which is
1 763 020 s, about 20.4 days.

Attempt budget and timeout are the kind's policy, not configuration.
Default 25 attempts, range 1 to 25. Default timeout 60 s, range 1 s to 1 h.
[Register kinds](../background-jobs.md#register-kinds).

### Timeout and summaries

A monotonic timer starts when the handler starts. At the deadline the
attempt's cancellation token fires and the handler task is aborted, which
takes effect at its next await. The outcome is recorded as timed out
without waiting for the task to stop. Blocking work the handler started
with `spawn_blocking` is not stopped by that cancellation, so the job may
run again while that work continues.
[Write a handler](../background-jobs.md#write-a-handler).

The stored summary is the handler error's display text, with every control
character, including NUL and newlines, replaced by a space, then cut to at
most 1024 bytes on a character boundary. Fixed texts replace content the
engine must not store:

| Case | Stored summary |
| --- | --- |
| Timeout | `attempt timed out after {timeout}`, in `humantime` form |
| Panic | `handler panicked`. The panic payload may quote data. |
| Payload does not decode | `payload does not decode as {kind}: {category} error at line {line} column {column}`, from `serde_json`'s classification, line, and column. The crate's own message can quote payload values. |
| Claim exhausted, no earlier failure | `attempt budget spent`, written by the claim |

### Retention

Every 60 s, first pass at once, each worker deletes `completed` jobs older
than 24 h and `failed` jobs older than 7 days, of every kind, registered or
not. Batches are 500 rows. Each batch is its own transaction, and its first
statement is `SET LOCAL statement_timeout = '1000ms'`. A pass deletes
completed batches until one deletes fewer than 500, then failed batches the
same way. `SKIP LOCKED` lets several workers share the work. Live jobs are
never selected. A terminal row never changes state, so a locked selection
is still terminal when it is deleted. Nothing else deletes a job.

Two statements, one per terminal state, so the literal state proves the
partial index's predicate in a generic plan. The `ANY` form replaced a
semi-join whose generic plan scanned the table.

```sql
DELETE FROM background_jobs
WHERE id = ANY (ARRAY(
    SELECT id FROM background_jobs
    WHERE state = 'completed'
      AND finished_at <= statement_timestamp() - $1
    ORDER BY finished_at
    LIMIT $2
    FOR UPDATE SKIP LOCKED))
```

The failed statement is the same with `state = 'failed'` and the 7-day age.

### Gauges

Every 10 s, first sample at once, with a 2 s statement bound
(`SET LOCAL statement_timeout = '2000ms'`). One query, two branches, so
each branch uses its partial index: due and scheduled counts, and the age
of the oldest due job, from `pending`; running counts from `running`. A
kind can appear in both branches. The worker sums rows per label. A
registered kind keeps its own name. Every other kind is
`<unregistered>`, counts summed, age the maximum. Every sample sets every
label the worker publishes, with zero for a label absent from the result.
A stranded kind's gauges return to zero once its jobs are gone, and never
keep a stale value.

## The worker process

[Jobs worker](runtime-lifecycle.md#jobs-worker) records the startup order,
the shutdown stages, and the exit codes. The points that fix the shape of
this process are here.

Registration is `jobs_worker::run(args, Option<Register>)`. The shipped
`main.rs` passes `None` and registers no kind. `None` refuses before
configuration, so the shipped binary refuses the same way in every
environment. The image check relies on that. The refusal is:

```text
no job kind is registered: register this service's job kinds in crates/jobs-worker/src/main.rs
```

A derived service passes a registration function. That function runs after
the configuration checks, so the default configuration refuses first with
`postgres.enabled must be true to run the jobs worker`, before registration
and before any database I/O.
[Register kinds](../background-jobs.md#register-kinds).

Listeners bind before claiming. Readiness admission runs after claiming has
started. A listener that cannot bind fails before any job is claimed, and
ready means claiming has started. Between bind and admission,
`/health/ready` answers not ready, not yet evaluated. A stop signal that is
already pending before claiming starts no engine. A signal during admission
abandons admission. Readiness never turns ready in either case, and the
exit code follows the shutdown plan.

The health listener reuses `infra_http::router()`, `harden`, and `Server`.
It serves the probe routes and the chain's 404 and 405 responses. No API
route, no OpenAPI document. `/metrics` stays on the diagnostics listener.

Worker identity is derived. There is no key for it.
`{service_name}-jobs-worker` is the OpenTelemetry `service.name`, the tracer
name, and the `service.name` field of the startup record. `application_name`
is the longest prefix of the service name of at most 51 bytes that ends on
a character boundary, then `-jobs-worker`, at most 63 bytes, which is
PostgreSQL's limit. A 64-character service name would otherwise lose the
suffix, because PostgreSQL cuts `application_name` silently at 63 bytes.
Instance id, version, commit, and environment follow the service's rules.
[Runtime Budget Policy](../configuration-source-policy.md#runtime-budget-policy)
records that no key controls the derivation.

The teardown tail after the drain is 17 s, not configuration: release 2 s,
listeners 2 s, background join 3 s, pool close 5 s, telemetry flush 5 s.
The worker refuses a grace period below `http.drain_timeout` plus that
tail. There is no readiness-propagation delay. The default drain is 25 s,
so the default worst case is 42 s inside the default 45 s grace, leaving
the same 3 s the service leaves for the runtime shutdown timeout (1 s) and
the tracer join slack (0.5 s).

The background join is 3 s, not the service's 5 s, because every joined
task is cancelled at its next await, and none waits for an attempt.
Attempts are drained and released before this stage. A claim loop still
inside a claim, its reconcile, or its own release after a forced drain is
dropped there. That is the runtime-shutdown residual below. A statement
dropped by cancellation keeps its connection until the server ends it, so
the pool close keeps 5 s.

A startup failure after the runtime exists goes through
`shutdown::abort_startup`: release within 2 s when the engine started,
close bound listeners within 2 s, cancel and join background tasks within
3 s, close the pool within 5 s when it is open. Telemetry is not flushed,
as on the service's startup-failure path.

A database outage after startup is not fatal. Claims, extensions, outcome
writes, retention, and gauge samples fail and retry at their own cadence.
The first failure and the recovery are logged, and every failure is
counted. Readiness follows the PostgreSQL probe. The process does not exit
because of the database.

## Connections

The worker refuses `postgres.max_connections` below `jobs.max_workers + 2`.
Size the database's `max_connections` across every instance and worker that
shares it. See
[Runtime Budget Policy](../configuration-source-policy.md#runtime-budget-policy)
and
[sizing](../background-jobs.md#configure-and-size-the-worker).

Each attempt slot holds at most one connection at a time: its handler's
while the handler runs, then its own outcome write. The engine's other
statements run one at a time under the single engine permit, so they hold
at most one connection. The readiness probe holds the last. Extensions
therefore never wait behind handler work. They wait at most for one other
engine statement.

A dropped statement keeps its connection busy until the server ends it, and
a handler aborted at its timeout may still hold its connection while its
outcome is written. Either briefly lowers the headroom by one, so an
extension may fail its 3 s acquire. The next upkeep round retries inside
the 28 s deadline.

The pool uses the same session budgets as the service: `statement_timeout`
and idle-in-transaction 8 s, acquire 3 s. A handler that needs a longer
statement sets `statement_timeout` for its own transaction only.
[Write a handler](../background-jobs.md#write-a-handler).

There is no `LISTEN` / `NOTIFY` path. A listener would hold a pooled
connection for the process lifetime and would need a third reserved
connection, and it loses notifications across reconnects, so polling would
stay anyway. A 1 s poll meets the pickup bound. An idle worker costs one
indexed statement per second.

## Observability

`record` is the one emitter of the attempt counter, the attempt records,
and the duration histogram. An outcome is recorded only when the database
proves it, and each admitted attempt is recorded once, by whoever takes its
registry entry. The accepted cases where a record can differ from what
happened are under
[Records follow the database](#records-follow-the-database).

The instruments are `jobs_attempts_total` (`kind`, `outcome`),
`jobs_attempt_duration_seconds` (`kind`; handler run time, for every attempt
that ran its handler), `jobs_live_jobs` (`kind`, `state` of `available`,
`scheduled`, or `running`), `jobs_oldest_available_age_seconds` (`kind`),
and `jobs_worker_operation_failures_total` (`operation`). `kind` on an
attempt is a registered kind. Gauges also use `<unregistered>`. Each worker
publishes the database-wide gauges, so aggregate them with `max`, not
`sum`.

The closed `outcome` set is `completed`, `retry`, `timeout`, `exhausted`,
`permanent`, `released`, `superseded`, and `lost`. An attempt that spends
the last unit counts as `exhausted`, not under its cause. The cause is in
the warn record's summary. `retry` is a retryable error, a panic, or an
undecodable payload, with budget left. `timeout` is a timeout with budget
left.

Records, none of which carry the payload: `job_failed` (`warn`),
`job_attempt_failed` (`info`), `job_attempt_completed` (`debug`),
`job_attempt_superseded` (`info`), `job_claim_lost` (`warn`, reason
`extension`, `record`, or `release`), and `jobs_operation_failed` /
`jobs_operation_recovered` (`warn` / `info`). The operation counter and
those two records are per operation: `claim`, `extend`, `record`,
`release`, `reconcile`, `retention`, `sample`. The failure class is
`acquire`, `begin`, `statement`, `commit`, `commit_unknown`, or
`timed_out`. The first failure after a success, and the first success after
failures, are logged per operation.

The attempt span is `job_attempt` at `info`, with `job.id`, `job.kind`,
`job.attempt`, and `otel.kind` of `consumer`. When the job stored a
`traceparent`, the span links to that enqueue context. No payload on the
span.

Field lists, buckets, and what a payload may hold are in
[metrics](../background-jobs.md#metrics-records-and-data-custody).

## Decisions Recorded Here

Research read 2026-09-24. Statements were executed against PostgreSQL 18.6,
the compose image. Code remains the factual authority. These are the
choices a later change should weigh before reopening them.

### Why the engine is template-owned

A template-owned engine on the existing sqlx 0.9 stack owns claiming,
leases, retries, rescue, and shutdown. No maintained crate with a stable
release fills the gap below. Candidates that accept the caller's sqlx 0.9
connection are a release candidate, an alpha, or a stable release that
migrates at worker startup and lacks default crash recovery, a per-attempt
timeout, and a non-retryable outcome. The stable engines with the right
semantics, awa and underway, are built on sqlx 0.8. Their typed enqueue
rejects the caller's connection, and adopting them would put a second
driver line and a second rustls provider into the build. The engine is
deliberately small: one job table, short claim statements, claim upkeep,
fenced outcomes.

No maintained crate with a stable release provides all four of these
together:

1. Enqueue shares the caller's already-open transaction on the caller's
   sqlx 0.9 connection, and a duplicate is a returned value rather than a
   failed statement. A failed statement aborts that transaction, and
   enqueue cannot open a savepoint to contain it.
2. The schema is owned by `migrations/`: no startup migration, no second
   migration writer or ledger to keep in lockstep, and no database
   extension.
3. Execution stays inside this pool's budgets and TLS stack: no transaction
   held across a job, short statements, one rustls provider (`aws-lc-rs`),
   and the admitted pool.
4. The execution contract under the composition root: persisted backoff, a
   per-attempt timeout, a non-retryable outcome, bounded recovery of a lost
   worker's job with fenced outcomes, survival of transient database
   errors, and a bounded drain driven by the root's cancellation.

Every sqlx 0.9 candidate misses at least two of these. Every sqlx 0.8
candidate misses the first and the third. Wrapping any of them would leave
the template owning most of the policy plus the crate's coupling.

| Candidate | Decisive reason |
| --- | --- |
| apalis-postgres 1.0.0-rc.9 | Release candidate. No persisted backoff. A duplicate aborts the caller's transaction and holds the key. Schema needs extensions or a second migration writer. |
| graphile_worker 0.13.5 | Startup always migrates. Crash recovery is off by default. No per-job timeout. No non-retryable outcome. One database error ends the run. |
| pgmq 0.34.0-alpha.7 | A visibility-timeout queue, not a job engine. Alpha. The published license, `PostgreSQL`, is outside the cargo-deny allow list. |
| awa 0.6.9 | sqlx 0.8. The typed enqueue rejects the caller's connection. The worker needs a second rustls provider. A unique conflict aborts the caller's transaction. |
| underway 0.2.0 | sqlx 0.8. The typed enqueue rejects the caller's connection. It holds one transaction open for the whole task, against the 8 s idle-in-transaction budget. |
| sqlxmq 0.6.0 | sqlx 0.8. No release activity since 2025-05-25. |
| fang 0.11.0 | Async enqueue owns its pool. No rescue of in-progress tasks. |
| pgqrs 0.15.3, rexecutor-sqlx 0.1.1 | No caller-connection enqueue. Both migrate into `_sqlx_migrations`, which collides with this template's history. |
| background-jobs 0.20.0, backie 0.9.0 | Not sqlx (`diesel-async`, `tokio-postgres`). background-jobs is AGPL-3.0. backie is archived. |

The Go template made the opposite choice. River meets the Go equivalents of
these constraints, so River owns the mechanics there. That reason does not
transfer.

### Design decisions

- **Template-owned engine in `infra-jobs`.** No maintained crate met the
  four items above. Adopting one was the strongest alternative, and it was
  rejected. The cost is owning and proving the mechanics. Reverse when a
  crate closes all four items. The watch list names the current candidates.
- **One table, `background_jobs`.** A claims table beside the job table was
  rejected. One table, short statements, and no extension are the size
  limit. The Go template's retired four-table queue is the counter-example
  this must not grow into. The cost is that claim upkeep writes the job
  row, so an enqueue under `REPEATABLE READ` can meet `40001` against a
  running holder after each extension. The guide names which engine writes
  touch a live job. See
  [enqueue](../background-jobs.md#enqueue-in-the-transaction).
  Reverse on a measured write rate on running rows that PostgreSQL cannot
  sustain.
- **Database-generated `uuid`, text at the SQL boundary.** A `bigint`
  identity was rejected. A provider key derived from the job identifier
  must stay unique across environments that share an account, and across a
  database rebuild. The cost is a 16-byte key, text conversion at the
  boundary, and no `uuid` feature in sqlx, so every crate keeps identical
  sqlx features and the image compiles sqlx once. Reverse when the
  template's minimum PostgreSQL becomes 18: default the id to `uuidv7()`
  by a forward migration, for index locality.
- **`payload` and `unique_key` as `bytea`.** `jsonb` and `text` were
  rejected. Only a database failure may abort the caller's transaction.
  `jsonb` rejects `\u0000`, and text depends on the server encoding, so
  validated input could still fail. The cost is that operators decode with
  `convert_from`. Nothing in view reverses it.
- **Fencing token `(id, claim_generation)`.** The attempts counter was
  rejected. A release gives its unit back, so the counter repeats, and a
  stale extension could extend a newer claim and break the 30 s recovery
  bound. An incremented generation was rejected too: a rolled-back claim's
  value would return. The token is drawn from a sequence, and an expired
  claim stays current until a newer claim replaces it. The cost is one
  `bigint` column and its sequence. Nothing in view reverses it.
- **Per-kind `LATERAL` claim, matched by `ANY (ARRAY(..))`.** One index
  scan over all pending jobs, filtered by kind, was rejected. A backlog of
  another kind, or of a stranded kind, must not cost each claim, and
  stranded jobs stay live indefinitely. The joined draft's generic plan
  scanned 110 250 rows. The cost is a longer statement, reviewed as a
  constant. Nothing in view reverses it.
- **Polling only, at 1 s.** `LISTEN` / `NOTIFY` was rejected. The pool
  reserves exactly two connections beyond the attempt slots. A listener
  holds a third, and notifications are lost across reconnects, so polling
  would stay anyway. The cost is up to 1 s of pickup latency, which the
  contract allows. Reverse when measured pickup latency below the poll
  interval is required, or when polling load matters. The reopened design
  adds `LISTEN` on its own reserved connection and raises the pool bound
  to `jobs.max_workers + 3`.
- **Worker composition in `crates/jobs-worker`.** A second binary in
  `crates/service`, or a shared runtime crate for both roots, was rejected.
  The initializer allows only the service binary and `openapi` as service
  binaries. The service's lifecycle code is binary-private. Extracting a
  shared crate would change every output that does not retain the pack, for
  a consumer only the pack has. The cost is about 150 lines of signal,
  budget, and tracing-options plumbing, mirrored from the service and owned
  by the pack. Reverse when a third composition root appears, such as a
  later outbox relay: extract a shared lifecycle crate then.
- **Registration through `jobs_worker::run(args, Option<Register>)`.** The
  shipped `main.rs` passes `None`. Declarative kinds with handler
  factories, and registration after the pool opens, were rejected. The
  shipped binary must refuse with the no-kind message before any database
  I/O, and a derived service's image check must stay deterministic.
  Handlers still need configuration and the task tracker to build clients.
  The cost is one `Option` in the entry point. The no-kind refusal comes
  before configuration only for `None`. Reverse when adopters need handler
  construction that depends on database I/O.
- **Each handler is its own task, owned by a supervisor.** `catch_unwind`
  around the handler inside the supervisor was rejected. A handler that
  never yields would block its supervisor, and with it the timeout and the
  drain. Aborted work may linger until it yields. The cost is that the
  aborted task can outlive its attempt until it yields or the runtime shuts
  down. Nothing in view reverses it.
- **Attempt-duration histogram, with jobs buckets, in `infra-telemetry`.**
  A summary was rejected. Per-kind durations must aggregate across workers,
  and `infra-telemetry` owns the recorder and its buckets. The cost is a
  private split of `Metrics::install` in every output. Behavior of that
  split is unchanged. Nothing in view reverses it.
- **Deterministic jitter from the job id and the attempt.** Random jitter
  was rejected. The contract needs a plus or minus 10 percent spread, the
  backoff must be unit-provable, and no random-number crate is declared.
  The cost is that jitter repeats for one job and one attempt. Nothing in
  view reverses it.
- **The health listener reuses `infra_http::router()`, `harden`, and
  `Server`.** A bespoke health router was rejected. The worker must serve
  the service's probe routes, bounds, and probe bodies. The cost is that
  the listener also emits the axum HTTP metrics for probes. Nothing in view
  reverses it.
- **Bind, then start claiming, then admit readiness.** Admission before
  bind, as in the service, was rejected. Ready means claiming has started,
  and a listener that cannot bind must fail before any job is claimed. The
  cost is that `/health/ready` answers not ready, not yet evaluated,
  between bind and admission. Nothing in view reverses it.
- **Teardown tail of 17 s.** A 20 s tail was rejected. The default drain of
  25 s plus 17 s is 42 s, which leaves the same 3 s the service leaves for
  the runtime shutdown timeout (1 s) and the tracer join slack (0.5 s). The
  cost is a background join of 3 s instead of the service's 5 s. Reverse
  when measured join or close times exceed their ceilings.
- **Identity `{service_name}-jobs-worker`, suffix kept by cutting the
  service name to 51 bytes.** A new key was rejected. No new key is
  allowed, and PostgreSQL silently cuts `application_name` at 63 bytes, so
  a 64-character service name would lose the suffix. There is no cost in
  configuration. Nothing in view reverses it.
- **Process proof uses `jobs-worker-fixture` in `integration-tests`.**
  Process tests and a fixture binary inside `crates/jobs-worker` were
  rejected. The process proof needs real PostgreSQL, which only
  `integration-tests` provisions, and test kinds stay out of the shipped
  binary. The binary is built only with the `integration` feature. The
  cost is one binary target on `integration-tests`. Nothing in view
  reverses it.
- **Four initializer parts borrow the `database-postgres` cache and save
  none.** A new cache per part, or fewer larger parts, was rejected. Parts
  must stay under the image job, and the Actions cache is already at its
  limit. The cost is four more runners per run. Reverse when those parts
  exceed the slowest other required job of a run: rebalance them.
- **`JOBS=none` equality with the baseline was proved once at delivery by
  a one-off comparison, not a standing CI check.** A standing comparison
  was rejected. The claim is a delivery claim, not a standing gate. The
  cost is that the proof is recorded, not re-run. It becomes a standing
  check if a later stage needs the comparison again.

### Rejected alternatives

- **apalis-postgres 1.0 now.** Release candidate, with API churn, and gaps
  on duplicate abort, schema ownership, and execution semantics. Reopen at
  a stable 1.0 that persists backoff and reports duplicates without
  aborting.
- **graphile_worker with a vendored schema and template wrappers.** The
  template would own recovery, timeouts, permanent failures, a restart
  loop, log filtering, and a migration lockstep across patch releases.
- **A sqlx 0.8 engine beside sqlx 0.9.** Two driver lines, a second rustls
  provider, DSN admission and session budgets re-implemented for 0.8, and
  enqueue through SQL the crate labels internal or through a type the
  compiler rejects.
- **pgmq as the primitive.** The template would still write every job
  semantic on top of a visibility timeout. The published license is outside
  the allow list.
- **Hold a row lock or a transaction for the duration of a job.** That
  collides with the 8 s idle-in-transaction budget, and with committing the
  claim before business work.
- **`LISTEN` / `NOTIFY` as the delivery path.** Notifications are lost
  across reconnects, and a listener holds a pooled connection. Polling is
  the correctness path. A notification may only shorten latency.

### Deviations from the Go template

| Go (River) | Rust decision | Reason |
| --- | --- | --- |
| River owns the mechanics | Template-owned engine | The gap above. River's Go equivalents of these constraints hold. The Rust candidates' do not. |
| Stuck-job rescue after 1 h, or timeout plus 1 h, with no heartbeat | Claims kept alive by upkeep. A lost worker's job is claimable again within 30 s of its last extension | Recovery is independent of attempt timeouts. The worker enforces timeouts itself, and outcomes are fenced, so fast recovery does not let a stale attempt overwrite a new one. |
| Unique states include `completed` | A unique key holds only while the job is live | Uniqueness stays independent of retention, and separate from effect idempotency, which the contract assigns to handlers. |
| An unknown kind fails and retries | A worker never claims a kind it does not register | Rolling deploys: new kinds wait for a worker that can run them, instead of burning attempts. |
| `StopAndCancel` counts the cancelled attempt | Attempts cancelled by the worker's own drain are given back | A deploy is not the job's fault. Lost workers still consume the attempt, which bounds poison jobs. |
| Readiness flag on the diagnostics listener | Health routes on a health-only application listener, with the PostgreSQL probe. Diagnostics serve metrics only | This repository keeps the diagnostics listener to `/metrics`. |
| Worker loads a filtered configuration | Worker loads the service's full configuration, like `migrate` | One loader, one precedence, one unknown-key rule, for every binary of the image. |
| Per-insert overrides of max attempts, queue, schedule, uniqueness, and priority, plus a per-worker timeout function | Per enqueue: a delay and a unique key. The attempt budget and the timeout are the kind's policy in the worker. No named queues or priorities | Producers stay data-only, and policy lives with the handler that knows the work, as River's timeout already does. The Go baseline also runs one default queue. |
| `jobs.max_workers` of 0 keeps the source worker inert | Default 1. No inert value | The worker runs only where it is deployed, and it refuses to start without a registered kind. 0 would be a dormant value. |
| One exit code for failure | `0`, `3`, and `1` | The template-wide degraded-shutdown code. |
| Parity kept | 25 attempts, `n^4` seconds with plus or minus 10 percent backoff, 60 s timeout, 1 s poll, retention 24 h and 7 days, `jobs.max_workers` as the only jobs key, a reusable binary without a job kind, a trace link from enqueue to attempt | River's defaults are the Go template's accepted behavior, and no Rust reason changes them. |

### Records follow the database

The database stays correct in each of these cases. Only the record can
differ from what happened. They are accepted.

1. **Runtime shutdown.** A statement still in flight when the runtime shuts
   down is dropped. If it had committed, claim expiry recovers its running
   claims, and its terminal writes are already correct. Nothing is recorded
   for it, as after a crash.
2. **Attribution after the deadline.** A reconcile whose result arrives only
   at or after the attempt's local deadline, and finds another claim,
   records `superseded`, even if the attempt's own retry or release took
   effect first. Once the claim's expiry can have passed, the row cannot
   tell the difference.
3. **Two possible writes.** At the drain end, a release whose commit is
   unknown, for an attempt that had settled a retry or a timeout, is
   recorded as that intended outcome when reconcile finds the job already
   claimed again. Either write may have released it.
4. **Never attributed.** A claim whose rows stay unattributed until the
   claim's local deadline is treated as not made. Claim expiry recovers its
   running rows, and its budget-spent rows keep no record. A supervisor
   write in the same state is recorded `lost` with reason `record`.

Reopen any of them if operators need exact records in these cases. The
reopened design adds a column naming the claim whose outcome last changed
the row.

### Reopen conditions and watch list

The affected decision is reassessed or reopened when one of the
following holds.

- Reassess replacing the engine when a maintained crate publishes a stable
  release that closes all four gap items under
  [Why the engine is template-owned](#why-the-engine-is-template-owned), as
  the Go template replaced its own queue once a crate met the same kind of
  constraint. The current watch list is awa 0.7 on sqlx 0.9 with a stable
  public SQL producer contract (`awa.insert_job`, awa issue #342),
  underway's next release on sqlx 0.9, apalis-postgres 1.0.0 with persisted
  backoff and non-aborting duplicates, and graphile_worker with optional
  startup migration and default recovery.
- Re-read every rejected candidate at a sqlx major upgrade of the
  workspace, and rerun the database proof when the proof image's
  PostgreSQL major version changes.
- A requirement that needs a long-held transaction or an extension. The
  engine is one table and short statements.
- Measured shutdown stage times beyond their ceilings. The tail is 17 s.
- Measured extension failures from acquire waits under full load. That is
  the pool arithmetic of `jobs.max_workers + 2`.
- A sqlx release that changes cancellation semantics. The 28 s deadline,
  the 3 s acquire, and the 12 s backstop absorb today's behavior: a dropped
  statement keeps its connection busy until the server ends it.
- Measured pickup latency below the poll interval is required, or polling
  load matters. The reopened design adds `LISTEN` on its own reserved
  connection and raises the pool bound to `jobs.max_workers + 3`.
- A measured write rate on running rows that PostgreSQL cannot sustain. One
  table; upkeep writes the job row.
- The template's minimum PostgreSQL becomes 18. Default the id to
  `uuidv7()` by a forward migration.
- A third composition root, such as a later outbox relay. Extract a shared
  lifecycle crate.
- Adopters need handler construction that depends on database I/O.
  Registration runs before any database I/O.
- A supported non-UTF-8 server encoding. The error summary assumes UTF-8.
  An outcome write that fails there is recovered by claim expiry within
  the budget.
- A different PostgreSQL major version with other plans or locking behavior
  for the claim, the retention deletes, or the `FOR SHARE` reconcile.
- A change to how the template tells its source from a derived tree. That
  is the presence of `template.lock`, read by the image check and the
  shipped-binary test. A derived service that adds or removes the pack by
  hand also sets `profiles.jobs` in `template.lock`
  ([Roll it out](../background-jobs.md#roll-it-out)).
- A derived service needs a non-goal: periodic schedules, priorities or
  named queues, per-kind concurrency, producer-side cancellation, an
  operator UI or API, completion inside the handler's transaction,
  workflows or stored results, per-kind backoff, or another datastore.
- A change upstream to a contract this pack keeps unchanged in every
  selection. The contracts are authentication, outbound HTTP, PostgreSQL
  (DSN admission, pool budgets, the transaction seam and its commit-outcome
  policy, and `migrate`), and HTTP idempotency behavior, including the
  adapter rule that admits the enqueue seam where both packs are retained.
  Such a change reopens whatever part of this pack rests on the changed
  contract, for example enqueue's atomicity with the caller's transaction and
  its uniqueness outcomes, the engine's transactions and operation bounds,
  its handling of an unknown commit, the worker's pool, and, where both packs
  are retained, the joint behavior inside the HTTP idempotency boundary.
