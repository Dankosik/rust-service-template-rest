# HTTP idempotency decisions

| Decision | Why | Reopen when |
| --- | --- | --- |
| Return a temporary conflict while the first command owns the key. | Waiting inside the writer pool spends a connection and the caller's deadline on work another request already owns. A retry hint lets the client try again after the owner finishes. A live key bound to different input requires a corrected request. [IETF §§2.6–2.7](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-08.html#section-2.6) · [PostgreSQL advisory locks](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS) | Observed conflict traffic breaches a service objective and bounded waiting can improve it without exhausting the pool. |
| Require a caller-generated key on operations that promise safe retries. Recommend a quoted random UUID and accept the published unquoted form. | After a lost response the client must already know the key for its next attempt. The IETF draft defines a Structured Field string and permits a service to require the header. Google AIP-155 makes its request-message field optional. Stripe also has clients that send an unquoted header. [IETF §§2.1–2.2, 2.7](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-08.html#section-2.1) · [AIP-155](https://google.aip.dev/155) · [Stripe](https://docs.stripe.com/api/idempotent_requests) | An operation has a durable request identity known to the client before the first send and can offer the same recovery guarantee without this header. |
| Isolate keys by verified caller and bind each key to one write. Compare the request representation the operation accepts. | Reusing a key for another resource, method or payload should expose the mistake. Hashing framed bytes also works for opaque payloads. Clients can resend their original bytes. [IETF §§2.2–2.4](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-08.html#section-2.2) · [AWS, different intent](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) | Distinct tenants can share a principal, or a client needs to reconstruct an equivalent request in a different representation. Define that operation's identity and preserve existing keys through their retry windows. |
| Replay the original committed outcome behind current authorization. | A caller recovering a lost response needs to know what the write decided. AWS accepts semantically equivalent responses, and AIP-155 permits current resource state in some cases. A local transaction can retain the original response even if the resource later changes. Keep preparation free of effects. Evaluate mutable business preconditions inside the fresh command so that a check such as “already exists” cannot hide a stored creation response. [AWS](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) · [AIP-155, stale successes](https://google.aip.dev/155#stale-success-responses) | The operation explicitly promises current state on retry or the stored representation cannot safely be returned under the caller's current permissions. |
| Store definitive business refusals explicitly. Permit retries of rolled-back transient failures. | Stripe v1 retains errors after execution begins, including 500s. Stripe v2 can resume failed work. A temporary database outage should leave the command retryable, while a lost definitive refusal should still be returned after the business condition changes. After an uncertain commit, a same-key retry can discover the durable decision. [Stripe v1](https://docs.stripe.com/api/idempotent_requests) · [Stripe v2](https://docs.stripe.com/api-v2-overview#idempotency) · [Brandur Leach](https://brandur.org/idempotency-keys) | A real operation introduces a final business outcome outside the supported catalog. Define its effect, replay and authorization semantics before adding it. |
| Keep local writes and their recorded outcome in one PostgreSQL transaction. Size the retry window for the service. | A local transaction closes the crash window on either side of commit. Products with different retry schedules choose different retention periods. A client arriving later needs a way to find its business operation. [Brandur Leach](https://brandur.org/idempotency-keys) · [IETF §§2.3, 2.5.2](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-08.html#section-2.3) · [Adyen, scope and validity](https://docs.adyen.com/development-resources/api-idempotency/#key-scope-and-validity-time) | A write must span independent stores or writers, a recipient can repeat an external effect, or the business identity must survive expiry or failover. Specify downstream deduplication, reconciliation and the required recovery point for that operation. |
