# Configuration decisions

`crates/config` owns the keys, defaults, decoding, admission rules, and
messages. This record keeps only rejected alternatives and reopen conditions.

| Choice / Rejected alternative | Decisive non-code reason | Reopen condition |
| --- | --- | --- |
| `config` (config-rs) with serde over `figment`, `confique`, `schematic`, or `smart-config` | config-rs is maintained and the most used; figment has had no release since May 2024; the schema-first crates are pre-1.0 or small. The loader already adds what they would bring: value-free rejections, strict scalar decoders, and secret admission. | config-rs loses maintenance, or a schema-first crate reaches 1.0 with value-free errors and secret parameters. |
| Collect independent errors at each stage of configuration loading | Operators can fix several source errors in one restart. Once all sources decode, operators can fix independent admission violations in one restart too. Typed checks require decoded values, and serde stops at its first decode error. | Decoding moves to a library that collects decode errors. |
| Read one generation from a Kubernetes AtomicWriter volume; leave publication of ordinary secrets directories to the mount provider | A startup can combine incompatible signing or TLS material if it follows the Kubernetes public links independently during rotation. An ordinary directory has no shared publication boundary for the loader to observe. | The mount provider exposes a portable atomic snapshot boundary. |
| Rules that need a parsed secret DSN (its scheme, credentials in the URL, TLS material on a plaintext address) stay in the adapter that owns the driver's DSN grammar and fail at bootstrap | `config` must not depend on adapters, and a second DSN parser in `config` could disagree with the driver; these rules surface one per restart, before any listener binds. | `config` and the adapters can share one dependency-free DSN parser per driver. |
| Handler-registration composition checks stay at bootstrap (`jobs-worker` messaging consumer vs producer keys, `jobs` pool capacity for registered ordinary jobs vs outbox, `http_idempotency` retention when idempotent operations are mounted) | They depend on which runtime handlers the binary registers rather than the binary role alone, which per-binary snapshots in `crates/config` already own. | Handler registration becomes declarative or static per binary. |
| No generated configuration reference (`schemars` JSON Schema, generated example TOML) | Section types and their doc comments are the reference; a committed generated file would have to be regenerated per template profile, and no editor or operator tool consumes a schema today. | An operator-facing tool or editor integration needs a schema, or derived services ask for a key reference outside the code. |
| `jiff` friendly durations (a `Span` with 24-hour days) over `humantime-serde` | `humantime` is unmaintained ([RUSTSEC-2026-0542](https://rustsec.org/advisories/RUSTSEC-2026-0542)); `jiff` is maintained and accepts the same unit and spacing forms. Months and years are refused because they have no fixed length. | `jiff` loses maintenance, or an accepted key needs a calendar-relative duration. |
