# Native gRPC decisions

`crates/infra-grpc`, `crates/infra-outbound-grpc`, `crates/grpc-contracts`,
`crates/config`, and `Cargo.toml` own the supported API, limits, metric names,
and dependency pins (with the client status hook in
[the tonic patch](../../vendor/tonic/PATCHES.md)). This
record keeps only rejected alternatives, protocol constraints, measurements, and
reopen conditions.

| Choice / Rejected alternative | Decisive evidence | Reopen condition |
| --- | --- | --- |
| Tonic `Routes` on the shared HTTP listener implementation, bound to its own port, over `tonic::transport::Server` | Reuses one bounded accept loop, connection cap, protocol sniff, and graceful drain instead of maintaining a parallel listener. | A gRPC listener policy cannot be expressed on the shared Hyper listener. |
| Handler validation + `tonic-types` (`google.rpc.ErrorInfo`) over `protovalidate` or a generated policy proxy | Avoids a 0.x CEL runtime and duplicate dispatch proxy when cross-language proto constraint evaluation is not required; `RESOURCE_EXHAUSTED` prevents retry storms that `UNAVAILABLE` triggers. | Cross-language declarative proto constraints become an accepted requirement. |
| Committed `tonic_prost_build` over Buf descriptor sets (with imports) vs `build.rs`, remote Buf plugins, or `prost-reflect` | Avoids codegen during ordinary builds and external plugin registries; `prost` panics on imported messages if `--exclude-imports` strips their descriptors. | Stock codegen cannot emit a required trait surface. |
| 2 KiB initial codec buffers over Tonic's 8 KiB default or 1 KiB | On 2,000 held bidi streams (DigitalOcean c-4), peak server RSS dropped from 20.9 MB to 12.4 MB with no CPU regression; 1 KiB cost +1.4% instructions on 1 KiB messages. | Typical contract messages exceed 2 KiB, or Tonic changes buffer growth. |
| Fixed HTTP/2 receive windows (8 MiB connection / 2 MiB stream) + `TCP_NODELAY` over adaptive windows | `h2` resets connections with `ENHANCE_YOUR_CALM` after ~140 unread frames < 256 B under the 65,535 B initial adaptive window; `TCP_NODELAY` cut 4 KiB unary latency on a 10 ms RTT loopback from 61 ms to 10.5 ms. | Bandwidth-delay product exceeds 2 MiB/stream, or hyper exposes `h2`'s `data_frame_budget` (in `h2` since 0.4.18, absent from hyper 1.12). The windows are also the memory a peer can pin: with every admission slot busy, 64 connections held 819 MB (12 MB each) against 135 MB with 1 MiB windows, at equal upload throughput for bodies up to 1 MiB, so shrink them once the budget is settable. |
| Bounded request-body drain on auth/shed rejection over immediate reply | Answering before reading in-flight `DATA` causes `h2` stream resets; past 1,024 resets Hyper sends `GOAWAY` (measured 16–1,250 collateral failed calls per 5 s auth-failure flood vs 0 with bounded drain). | Hyper stops counting late `DATA` toward `GOAWAY`, or a measurement shows the drain costing more than a raised `max_local_error_reset_streams` cap. Hyper 1.12 exposes that cap (default 1,024), but raising it lifts the reset-flood ceiling of [RUSTSEC-2024-0003](https://rustsec.org/advisories/RUSTSEC-2024-0003.html) for every connection, while the drain avoids the resets. |
| Two admission bounds of `grpc.max_in_flight` each, openings before authentication (held to response headers) and authenticated calls (held to terminal status), over one permit held from opening to terminal status | With one permit, calls stuck in slow authentication take the slots of open streams: at 256 slots with 250 streams open, about 6 slow authentications refuse every new caller instead of 256 (`opening_and_terminal_capacity_have_independent_lifetimes`). Up to twice `max_in_flight` admitted calls is the accepted cost. HTTP keeps one bound because its permit ends at response headers. Both protocols share the wait rule in `infra_http_transport::acquire_within`. | Streaming calls leave the supported contract, or a measurement shows that authentication spent on calls the terminal bound then refuses matters. |
| Thin server `tracing` span + `grpc-ecosystem` Prometheus series over `tracing_opentelemetry_instrumentation_sdk` | JSON logging serializes span fields on creation and every `Span::record`; the thin span cut 15% of instructions and 20 allocations per unary call while preserving standard `go-grpc-middleware` dashboard queries. Server series carry its `grpc_type` label from descriptor streaming flags; client series omit it because generated-client metadata (`tonic::GrpcMethod`) has no streaming kind, and per-message `msg_received`/`msg_sent` counters are not emitted. Span attributes follow the stable OpenTelemetry RPC conventions (v1.45.0) directly, without the `OTEL_SEMCONV_STABILITY_OPT_IN` duplicate mode: the template has no published major version, and a derived service adopts the rename in its reviewed template upgrade. | OpenTelemetry `rpc.*` metric conventions replace `grpc-ecosystem` dashboards, or tonic exposes streaming kind to client middleware. |
| Client HTTP/2 keepalive PING at 60 s (active calls only), single channel per service/mesh address, no compression, startup-read PEM | Faster idle pings trigger `GOAWAY too_many_pings` on `grpc-go` / `grpc-java` / C-core servers; service meshes own endpoint discovery; same-network compression rarely repays CPU. Default `grpc-go` and C-core enforcement (5 min) also counts pings on an open stream on which the server sent nothing since the last ping, so a silent long-lived `ClientTimeout::OpeningOnly` stream to such a peer needs a peer policy that permits 60 s pings. | Direct headless DNS balancing, payload compression, sub-restart cert reload, or silent long-lived streams to default-policy peers becomes required. |
| HTTP/2 on the gRPC listener only; the HTTP listener speaks HTTP/1.1, over serving both protocols on the HTTP listener | The two HTTP/2 hazards measured above applied to the HTTP listener without their remedies: it answers 503, 413, 401 and 400 before reading the request body with no bounded drain (the `GOAWAY` row), and a cleartext HTTP/2 peer could pin the 8 MiB / 2 MiB windows on the application and diagnostics ports. Protocol detection also ran its own `header_read_timeout` before hyper's, so a slow first request held a connection slot for up to twice the setting. | A deployment needs HTTP/2 between its proxy and the HTTP listener; the early answers then need the bounded drain. |
