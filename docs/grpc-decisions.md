# Native gRPC decisions

The [adoption guide](grpc.md) owns the supported API and operator contract.
Each row is the present boundary, the alternative it beat, the decisive
reason, and the condition that would reopen it.

| Decision | Rejected alternative | Decisive reason | Reopen |
| --- | --- | --- | --- |
| Tonic `Routes` on the existing `infra_http::Server`, including `bind_tls` | Tonic's transport `Server`: a second accept loop without this template's connection cap and protocol-sniff deadline, plus a drain the process cannot budget. The previous hand-written HTTP/2 server: it duplicated the listener without keepalive or idle bounds, and span-in-body custody cost about 1300 lines. | One accept loop already has the cap, protocol-sniff deadline, HTTP/2 keepalive, accept backoff and a tracked connection set it can drain. gRPC drain is the same `Server::drain` as HTTP. | Reopen only if tonic exposes a supported server whose accept and drain the process can budget without a second loop. |
| Tower, tower-http and axum middleware on the tonic router | A generated policy proxy in front of every method | Registration is `Services::add(EchoServiceServer::new(...))`. Handler statuses pass through. A proxy duplicated tonic dispatch to enforce policy that middleware and handlers now own. | Reopen if a feature must intercept every cardinality inside the generated trait and middleware cannot see that call. |
| No protovalidate. Handlers validate input, as HTTP extractors do. The example checks length and returns an `infra_grpc::Failure` with a field violation. | The removed path: a third-party 0.x CEL bridge, a protoc build dependency through `prost-protovalidate-types`, and a custom codec | Shared cross-language constraints were not a requirement. The bridge added a compiler and a second decode path for rules the handler can state directly. | Reopen if cross-language shared constraints become a requirement. |
| `infra_grpc::Failure` is the gRPC projection of the failure catalog: the catalog code fixes the status code and message, `google.rpc.ErrorInfo` carries the code in upper case under the service name as domain, and `BadRequest` and `RetryInfo` come from `tonic-types`. The middleware answers its own rejections with it. | A `Meaning` enum and `ClassifiedFailure` in `service-failure`; bare `Status` values from the middleware; lowercase reasons under a fixed `service` domain | `Meaning` mapped one to one onto `tonic::Code` and only gRPC read it, so a REST-only service kept it unused, and a bare middleware status gave a gRPC client no code where HTTP gave one. `error_details.proto` asks for an `UPPER_SNAKE_CASE` reason and the service name as domain. The shed stays `RESOURCE_EXHAUSTED` under the reason `SERVICE_UNAVAILABLE`, the identity HTTP's shed uses, so a client that retries `UNAVAILABLE` adds no load. | Reopen if another transport needs a class coarser than the catalog code, or a consumer needs the reason spelled as the HTTP code. |
| Stock `tonic_prost_build` over Buf's file descriptor set, built with imports | A custom service generator, remote Buf plugins, `build.rs` generation, or a set built with `--exclude-imports` | Buf owns parse, STANDARD lint and FILE compatibility. Prost's `include_file` builds the package module tree, so the tool only calls stock codegen, which emits the native traits. Well-known types map to `prost_types` and emit nothing. Without the imports prost panics on the first imported message type, because it reads that message's descriptor to choose derives. Remote plugins add registry availability. `build.rs` would generate during ordinary service builds. | Reopen if stock codegen cannot emit a required native trait option and a local generator is the smallest fix. |
| Generated code uses `grpc_contracts::codec::ContractCodec`: tonic's prost encoder and decoder with 2 KiB initial buffers (`codec_path`) | Tonic's default 8 KiB `BufferSettings`; 1 KiB buffers | Tonic allocates both buffers for every open call. On 2000 held bidi streams server peak memory fell from 20.9 to 12.4 MB with no measured CPU change (DigitalOcean c-4, loopback, 3 interleaved rounds). 1 KiB saved more memory but cost 1.4% instructions per call on 1 KiB messages. | Reopen if a contract's typical message exceeds 2 KiB, or tonic changes its buffer growth. |
| Opt-in server reflection: `Services::add_reflection` serves `tonic-reflection` 0.14.6 over the described sets, as business routes, in both protocol versions (`grpc.reflection.v1` and `grpc.reflection.v1alpha`) | No reflection, with `buf curl --schema api/proto` only; always-on or public reflection; a hand-written reflection service; a second descriptor argument beside `Services::describe`; `v1` alone | `grpcurl`, `grpcui` and Postman need reflection or the schema files. `tonic-reflection` ships in tonic's own release train at the pinned version and adds no new transitive crate. The sets are the ones `describe` already read, so reflection cannot serve a schema the transport does not know, and it is built when the router is, so the order of `describe` and `add_reflection` does not matter. Behind the business chain it needs the caller's bearer; the registration decides per environment, because it publishes the whole schema. grpc-go's `reflection.Register` serves both versions because tools released before `v1` ask only for `v1alpha`; the second server reads the same sets and costs one more route. | Reopen if a deployment must expose reflection to unauthenticated tooling, or the `grpc` crate replaces tonic's reflection service. Drop `v1alpha` when tonic-reflection does. |
| Deadline measured to response headers, tonic `Server::timeout` placement, status `DEADLINE_EXCEEDED`, cap `grpc.request_timeout` (default 8 seconds). It is the outermost business layer, so it covers authentication | A body-lifetime timer, tonic's native timeout code (`CANCELLED`), or a constant cap; a deadline that starts after authentication | Header placement matches tonic's server timeout. The status matches the shared deadline meaning. Client-streaming must finish the upload inside the cap; server and bidi streams are then bounded by the caller and process drain. The cap is the operator's, like `http.request_timeout`; configuration refuses one that does not fit the drain both listeners share. A deadline that started after authentication let a slow introspection or key fetch run for the verifier's own three seconds while the caller had asked for less, and HTTP's request timer already covers its authentication. | Reopen if one service needs different caps for different methods. |
| Clients use tonic `ClientTlsConfig` (TLS 1.2 and 1.3, normal verification). The server stays TLS 1.3-only. | The custom connector that forced client TLS 1.3 | The client would have rebuilt rustls only to diverge from tonic's normal verification. The server already builds its own config, so the 1.3 floor has no extra cost. | Reopen if an accepted peer requires a client protocol floor tonic cannot set. |
| Observation uses `tracing-opentelemetry-instrumentation-sdk` gRPC span helpers, already locked through axum-tracing-opentelemetry, and follows a call to its status: the response headers of a Trailers-Only answer, otherwise the trailers, read by a pass-through body | `tonic-tracing-opentelemetry`, an extra crate for the same helpers; header-only observation, as before; the removed custom server's span custody | At the headers a stream has no status yet: one that failed or panicked after its first message was counted `OK`, and its handling time was the time to the first header. grpc-go's interceptors and tower-http's gRPC classifier read the trailers, and the OpenTelemetry conventions ask a call's metric to equal its span's duration. The body wrapper is about sixty lines beside the HTTP adapter's own active-request body, spawns nothing and buffers nothing; the removed custody cost came from the hand-written server it lived in, not from reading trailers. The deadline and the concurrency permit stay at the headers. | Reopen if a maintained helper reads the trailer status itself. |
| Small tonic-health adapter over `ReadinessReader` | `HealthReporter` | The stock reporter starts `SERVING` and answers unknown `Watch` with `NOT_FOUND`. This adapter reads readiness, returns `NOT_FOUND` for unknown `Check`, emits `SERVICE_UNKNOWN` for unknown `Watch`, and ends after `NOT_SERVING` at drain. | Reopen if tonic-health can start from an external verdict and end unknown `Watch` as `SERVICE_UNKNOWN` without a spawned reporter task. |
| OAuth eviction at the initial response only | Trailer inspection | Real servers reject authentication with a Trailers-Only response, whose `grpc-status` arrives in the initial headers. Trailer inspection holds the body. The response is returned unchanged. | Reopen if an accepted provider rejects machine auth only in trailers and a supported hook can see that without a body inspector. |
| Server `grpc_service` and `grpc_method` come from the path only when it is a described method of a registered service or of health; otherwise both are `"unknown"`, in the labels and in the span name | Labeling every raw path; or labeling only calls a generated service answered, which put every authentication failure, shed, deadline and recovered panic under `unknown` | The described methods are a closed set, so a caller-chosen path still cannot create a series, and the outcomes an operator alerts on, deadlines above all, are split by method. `go-grpc-middleware` initializes its series from `GetServiceInfo`, the same closed set. | Reopen if a service must serve a method no descriptor set describes. |
| Metric names and labels follow the grpc-ecosystem Prometheus convention (`grpc_server_started_total`, `grpc_server_handled_total`, `grpc_server_handling_seconds`, `grpc_client_*`, `grpc_code` as the grpc-go code name), with that convention's meaning: handled when the call's status is known, handling time for the whole call. A call its caller abandons before its status is handled as `Canceled` | The previous template-specific `grpc_calls_total{method,direction,outcome}`, whose outcome folded `FAILED_PRECONDITION`, `OUT_OF_RANGE`, `UNKNOWN` and `DATA_LOSS` into `internal`; handled counters without a started counter; recording nothing for a dropped call; the same names measured to the response headers | Standard names let existing dashboards and alerts apply, and every code stays distinct; a client error such as `FAILED_PRECONDITION` no longer looks like a server fault. The names only help if they mean what `go-grpc-middleware` means by them, which is the finished call. Started minus handled is the calls in progress, which needs every started call to be handled: a drop guard records the abandoned ones, as grpc-go records a cancelled context. The label set is bounded: registered services, described methods, 17 codes. `grpc_type` and the per-message counters are left out: the client side cannot know a call's type, and no accepted dashboard reads them. | Reopen if the service adopts OpenTelemetry metrics export and must emit the `rpc.*` semantic-convention instruments instead. The RPC conventions are a release candidate (2026-10) that renames the span attributes to `rpc.system.name`, a fully qualified `rpc.method` with no `rpc.service`, and a string `rpc.response.status_code`; rename the four attributes in `observe.rs` when they are declared stable. |
| `grpc_server_failures_total{grpc_service, grpc_method, failure_code}` and the span attribute `failure.code` record the catalog code of a failed call. The observer reads it from the `google.rpc.ErrorInfo` of the status tonic leaves in the response extensions or stream trailers, and counts a recovered stream panic as `internal_error`; only a reason under `ERROR_DOMAIN` that the catalog publishes becomes a label | A `failure_code` label on `grpc_server_handled_total`; a per-call access log as HTTP has; labeling any `ErrorInfo` reason | Several catalog codes share one gRPC code, and nothing told them apart on the gRPC side while HTTP logs `problem_code`. A label on the handled counter breaks the grpc-ecosystem series standard dashboards query; the transport has no per-call log and one counter answers the question without adding one. The catalog bounds the label, so a handler's own reason cannot create a series. | Reopen if an accepted failure cannot carry the catalog reason in its status details. |
| Health (`Check` and `Watch`) is public; authentication wraps business routes only | Public `Check` with bearer-protected `Watch`, selected by a path comparison inside the authenticator | Load balancers and Kubernetes gRPC probes call health without credentials, and exempting the whole health service is the usual interceptor practice. Health reveals only readiness. A `Watch` stream is bounded by the connection cap and the HTTP/2 stream limit and ends at drain. | Reopen if an accepted threat model requires credentials for readiness information. |
| The business concurrency limit holds its permit until response headers | A body-lifetime permit | The `admit` permit is released when the handler's response future resolves, matching the header-bound deadline. Unary and client-streaming calls are fully bounded; open server-streaming and bidi streams are bounded by the connection cap and the HTTP/2 stream limit. | Reopen if a service with long server or bidi streams needs its own stream budget; add a body-held permit for that service. |
| Bearer parsing, verification and the `authn_verifications_total` outcome live in `Verifier::authenticate`, shared by HTTP and gRPC | A copy of the parse-and-verify sequence per transport | One owner keeps both transports' outcomes and `cancelled` accounting identical; each transport maps `Failure` to its own response. | Reopen if a transport needs a verification step the other must not take. |
| Required scopes are declared per method path with `Services::require_scopes`, checked against the described methods, and enforced by the authentication middleware | A custom method option in the proto; a scope check called by each handler; a path whose method name nothing checks | Authorization policies in grpc-go `authz` and Envoy also match the request path. The middleware already holds the verified principal, so the denial precedes the handler on every cardinality, as the OpenAPI scopes do on HTTP. `Services::describe` reads each method from the committed descriptor set, so a misspelled path fails startup instead of protecting nothing. A proto option would still need an extension-aware reflection crate (prost does not decode extensions) for one list of strings. | Reopen if scopes must be read by other languages from the schema itself; then move the declaration into a method option. |
| `Services::describe` reads an encoded `FileDescriptorSet` with `prost-types`; a server is added only for a described service | Method lists written by hand next to each registration; a generated constant per method from a custom codegen step; `prost-reflect` | A generated tonic server exposes its name but not its methods. The descriptor set is already committed for reflection and is what Buf checks, so it is the one list that cannot drift from the contract. `prost-types` 0.14.4 is prost's own crate, already in the lock through `tonic-types` and `tonic-reflection`, and decoding names needs nothing `prost-reflect` adds. | Reopen if tonic's generated servers start listing their methods. |
| The registration hook receives `service::AppState` | `fn(&mut Services)` with no state, which left a generated server no way to reach a dependency bootstrap opened; a boxed closure built before bootstrap | HTTP handlers get feature state through `State`; a generated server gets the same value when it is constructed. The hook stays a plain function called once inside bootstrap, after the dependencies exist. | Reopen if a server needs a dependency that must not be visible to HTTP routes. |
| `grpc.max_in_flight`, `grpc.max_connections` and `grpc.max_connection_age` are configuration, with the HTTP defaults for the first two | Constants in the crate | The right concurrency depends on the handlers and the replica size, which only the operator knows; HTTP already exposes the same bounds. | Reopen if a bound must differ per service on one listener. |
| Connections get GOAWAY after `grpc.max_connection_age` (default thirty minutes, spread by 10%), implemented once in `infra_http::Server` | No age, as before; tonic's `Server::max_connection_age`, which needs tonic's accept loop; a forced close after a grace period | See the listener row in [HTTP Architecture](architecture/http.md): a channel keeps one connection for the life of its process, so without an age a connection-level balancer never rebalances it. Open calls finish; the client reconnects for the next one. A grace bound would cut health watches and long streams that are otherwise legitimate. | Reopen if a stream that outlives the age must be bounded; add the grace then. |
| A client call whose own `grpc-timeout` ran out is `DEADLINE_EXCEEDED` | The previous single `UNAVAILABLE` for every channel error; tonic's `Status::from_error`, which reports the expiry as `CANCELLED` | The channel enforces `grpc-timeout` itself and reports `TimeoutExpired`. Mapped to `UNAVAILABLE`, a caller that retries that code repeated a call the server might still be running. gRPC assigns `DEADLINE_EXCEEDED` to an expired deadline. Other channel errors stay `UNAVAILABLE` with a fixed message. | Reopen if tonic maps the expiry to `DEADLINE_EXCEEDED` itself. |
| Client HTTP/2 keepalive PING every 60 seconds, only while a call is open | The previous 20 seconds | gRPC's keepalive guide asks clients not to ping much more often than once a minute; grpc-go, grpc-java and C-core servers answer a client that pings a quiet stream too often with `GOAWAY too_many_pings`. A dead peer is still found within 80 seconds. | Reopen if a deployment needs faster detection and controls the server's ping policy. |
| TLS material is PEM text read once at startup; a rotated certificate takes effect on restart | Certificate files watched and reloaded in process through a rustls `ResolvesServerCert` | An orchestrator can inject a rotated Kubernetes `Secret` into the same environment variables and restart the pods, which is how the template already takes every other secret. In-process reload needs a file watcher and a background task this transport does not otherwise have. A verified client certificate admits the connection and is not passed to handlers, because the bearer is the identity. | Reopen if certificates rotate more often than a rolling restart can follow, or a handler must authorize by certificate. |
| The gRPC port serves through the shared `auto` builder, so a plaintext listener also parses HTTP/1 | An HTTP/2-only builder for this listener | The HTTP listener already exposes the same HTTP/1 parser with the same limits, and an HTTP/1 request to a tonic route gets no gRPC answer. A second builder is a listener difference with no accepted threat behind it. | Reopen if the gRPC port faces a network the HTTP port does not. |
| A handler passes its remaining deadline to an outbound call itself, with `infra_grpc::grpc_timeout` and `Request::set_timeout` | Automatic propagation through a task-local set by the middleware | Tonic has no supported propagation hook, and a task-local is lost in every spawned task. The inbound deadline already cancels the handler future, which drops its outbound calls. | Reopen if the `grpc` crate ships deadline propagation. |
| `Client::new` rejects a destination whose scheme disagrees with `ClientSecurity` | Trusting the configured security alone | Tonic applies TLS only to an `https` URI, so `http` with TLS material would connect in plaintext and send bearer tokens in clear. | Reopen if tonic starts refusing TLS configuration on an `http` URI itself. |
| `Client::new` takes the longest wait for a call's response headers, applied with tonic's `Endpoint::timeout` | No client bound, as before, so a call without `Request::set_timeout` waited until keepalive gave up on the connection; writing a default `grpc-timeout` into every call; a configuration key | gRPC's guidance is that every call has a deadline. A required argument makes the adapter choose one, as `infra_outbound_http::Limits` does. `Endpoint::timeout` bounds this side to the response headers and tells the server nothing, so an open response stream is not cut; a default `grpc-timeout` would make every peer end long streams at it. A call's own shorter `grpc-timeout` still wins and still reaches the server. | Reopen if operators must tune the bound per deployment; add `integrations.<name>.grpc.timeout` then. |
| A `Client` is one connection with no name resolver or balancer | tonic `Channel::balance_list` over a fixed address list; a hand-written DNS watcher feeding `balance_channel` | A service address behind a balancer or mesh is one name, and the server's `grpc.max_connection_age` already moves a channel between replicas. tonic has no resolver; watching DNS would be this template's own mechanism for what the `grpc` crate is building. | Reopen when the `grpc` crate ships a server-compatible channel with resolvers, or a dependency is addressed by a headless name with no balancer in front. |
| No message compression: tonic's `gzip`, `deflate` and `zstd` features stay off | Enabling `gzip` and accepting it on every generated server | gRPC clients do not compress unless told to, and service-to-service payloads on one network rarely repay the CPU. A feature would add a codec dependency and a decompression bound to own for no accepted caller. | Reopen when an accepted peer sends compressed messages or a contract carries large compressible payloads. |
| The replacement fixed five listener and status defects: no HTTP/2 keepalive or idle bound, a spinning drain loop, accept errors without backoff, silently suppressed panics, and malformed bearer mapped to `INVALID_ARGUMENT` | Patching those inside the custom server | The shared listener already had keepalive, the first-byte bound, 50 ms accept backoff and `GracefulShutdown`. The observation layer's `catch_unwind` leaves the payload to the normal hook. Malformed bearer is `UNAUTHENTICATED`. | Do not restore the custom listener to fix one of these. Reopen a single defect only if the shared listener loses that bound. |
| The server span carries only `otel.name` and `otel.kind` as `tracing` fields; RPC attributes are set on the OpenTelemetry span, and nothing is `Span::record`ed | `tracing_opentelemetry_instrumentation_sdk::grpc_server::make_span_from_request` with twelve fields and two records | The JSON log layer serializes every span field at creation and again on each record. On DigitalOcean c-4 the SDK span was 30% of a unary call's instructions; the thin span cut 15% of instructions and 20 allocations per call, the same shape the HTTP adapter uses. | Reopen if a log reader needs an RPC attribute on every line inside a call. |
| Metric handles are registered once per method and kept by the router and each `Client` | `metrics::counter!`/`histogram!` with owned label strings on every call | Four label strings and two recorder lookups per call cost 3-4% of instructions and 14 allocations. Only paths a generated service answered are kept, so the map is bounded by the methods. Handles bind to the recorder installed when the first call is recorded, as the bootstrap installs it before serving. | Reopen if a process must swap its global recorder after serving starts. |
| Handling-time histograms register the Prometheus default buckets | No bucket entry, which the recorder renders as a summary | `go-grpc-middleware` dashboards query `grpc_server_handling_seconds_bucket`; summary quantiles cannot be aggregated across replicas. | Reopen if an SLO needs a finer bucket below 5 ms. |
| Two business middlewares: `deadline` outside authentication, `shed` inside it with `Semaphore::try_acquire_owned`, added only when a limit is configured | `HandleErrorLayer`, `load_shed`, `GlobalConcurrencyLimitLayer`; one middleware for both inside authentication, as before | Same shedding behavior (no queueing, permit to response headers) with fewer layers than tower's. They are two because they sit on opposite sides of authentication: the deadline must cover it, and the limit must not count a call that failed it, or a flood of bad bearers could shed real callers. The split costs one boxed future per call. | Reopen if calls must queue for a permit. |
| A rejected call (authentication failure, shed) is answered after reading its request body, bounded by 100 ms and 64 KiB | Answering immediately | The caller's DATA arrives after the answer; h2 resets each such stream and after 1024 resets per connection hyper sends GOAWAY, failing every other call on that connection. Measured: 16-1250 failed calls per 5 s authentication-failure flood, p99 42 ms; with draining, none and p99 5 ms. | Reopen if hyper exposes h2's reset-stream retention for servers, or the limit stops counting late DATA. |
| `TCP_NODELAY` and HTTP/2 adaptive windows on the shared listener and the client | Nagle and fixed 1 MiB windows | Measured on DigitalOcean c-4 with a 10 ms loopback RTT: a 4 KiB unary call took 61 ms (delayed ACKs) and 10.5 ms with both; a 1 MiB unary call 43 to 13 ms; a 4 MiB server stream 84 to 23 ms; a 2 MiB client stream 157 to 16.5 ms. Without RTT, client-streaming p50 fell from 42 to 8 ms. A saturated single-core bidi echo loses about 40% messages per second without Nagle's batching, the cost tonic and grpc-go also accept. | Reopen if a deployment is bound by small-message bidi throughput on one core. |

Eviction reuses `Credentials::reject`. Real servers reject authentication
with a Trailers-Only response, whose `grpc-status` arrives in the initial
headers. It runs only when that response has `grpc-status` `UNAUTHENTICATED`,
or HTTP 401 and no `grpc-status`. Trailers are not read. The response is
returned unchanged.
Eviction is an in-memory update and starts no background work. `PERMISSION_DENIED` keeps the credential. A caller-supplied
`Authorization` is `INTERNAL` before acquisition (gRFC A54). Reopen if an
accepted provider rejects machine auth only in trailers and a supported hook
can observe that without a body inspector.
